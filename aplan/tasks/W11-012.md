## Why

dprint is mature evidence for parallel Wasm and process plugin modes, but it uses application-specific core-Wasm and process protocols with callbacks, cancellation, state, and distinct schema versions.

## Acceptance criteria

- [ ] pin current Wasm/process schema versions and map their implementations, SDK traits, configuration flow, framing, callbacks, cancellation, concurrency, and compatibility policy
- [ ] identify concrete duplicated semantic values between the two protocols and deliberate differences that should remain
- [ ] classify the shared value subset and every incompatible lifecycle feature against witforge 0.4
- [ ] evaluate a bounded next-generation contract or message sub-contract without proposing a disruptive replacement of the mature ABI
- [ ] distinguish stable protobuf/schema/versioning benefits from process runtime concerns witforge does not own
- [ ] record migration cost, likely benefit, and go/no-go recommendation
- [ ] record the canonical outreach path: a searched, focused GitHub issue because the repository has no Discussions channel

## Why it is untestable

This task records external protocol research; no local behavior changes.
