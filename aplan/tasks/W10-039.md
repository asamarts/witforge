## Why

Audit finding E1 (high). `action/index.js:15` builds the environment key with
`name.replaceAll('-', '_')`, so it reads `INPUT_DIFF_OLD`. The runner only uppercases the
input name and replaces spaces, so the variable it sets is `INPUT_DIFF-OLD`. Every hyphenated
input (`diff-old`, `diff-new`, `diff-check`, `github-token`) is therefore read as empty. The
documented CI snippet (README, `docs/guide/ci.md`, `docs/design/action.md`) passes
`diff-old`/`diff-new`, so `witforge diff --check` never runs and a breaking contract change
passes a consumer's CI. `latest` lookups are also always anonymous.

Verified 2026-11-18 against GitHub's metadata-syntax reference ("converts input names to
uppercase letters and replaces spaces with `_` characters"; its example reads `num-octocats`
as `INPUT_NUM-OCTOCATS`) and against `getInput` in `@actions/core`
(`name.replace(/ /g, '_').toUpperCase()`). Not observed on a hosted runner. Nothing catches it
today: `input()` is not exported or tested in `action/test.js`, and no workflow in this
repository passes a diff input.

## Reproduction

```sh
env 'INPUT_DIFF-OLD=wit/v0.1' node -e '
  const name = "diff-old";
  const read = (key) => JSON.stringify(process.env[key] || "");
  console.log("action reads:", read("INPUT_" + name.replaceAll("-", "_").toUpperCase()));
  console.log("runner sets: ", read("INPUT_" + name.replace(/ /g, "_").toUpperCase()));'
```

The first line prints `""`, the second `"wit/v0.1"`. With an empty `diffOld`, `buildCommands`
plans no `witforge diff` command.

## Decision

Decided by the owner on 2026-11-19: this branch is delivered as a pull request, and
the hosted run of that pull request supplies the log the third criterion asks for.
The task closes on that log, on the commit that fixed `input()`, and on the
Action's unit tests, which `cargo test` runs as
`action_unit_tests_pass_under_node` (`crates/witforge-cli/tests/tooling.rs`).

Found while reviewing the fix on 2026-11-19, and changed with it:

- With `github-token` actually read, the token would also have been sent with the
  archive and checksum downloads. It is now sent only to the latest-release
  query. `action.yml` and `action.md` say so, and `action/test.js` asserts that a
  download carries no `Authorization` header.
- The documented snippets passed `diff-old` and `diff-new` and left `diff-check`
  at its default. With the inputs read, that snippet fails on any breaking view,
  including an added record field, and it fails on `examples/evolved`. The README
  and the CI guide now run `witforge diff` as a separate reporting step. The CI
  guide and the changelog say that a workflow which already passes the inputs
  starts gating when its pin moves past v0.5.0.

## Edge cases

- The names come from `action.yml`: `action/test.js` reads every declared input
  through the runner's naming rule, so an input added later is covered without an
  edit to the test.
- An input name with a space maps to `_`; a hyphen stays. No declared input has a
  space today.
- A caller that exports the old underscore names itself (`INPUT_DIFF_OLD`) is
  ignored, and `action/test.js` asserts it.
- `diff-check` is compared case-insensitively with `false`. Anything else,
  including an empty value, gates.
- One of `diff-old` and `diff-new` without the other is an error. It is raised
  after the download; validating before it is `W10-086`.
- The CI gate step is expected to fail, and its outcome cannot tell a failed gate
  from a failed install. The reporting step before it installs the same release
  on the same runner, so an input regression, which fails every run, is not hidden
  by one transient download failure. Asserting which command failed is `W10-086`.
- The hosted proof is on Linux. The other three platforms run the published
  `v0.5.0` Action, which has the defect and is given no diff input. They prove the
  fix only when the tagged 0.6.0 Action runs there (`W10-069`).
- `cargo test` skips the Action's unit tests with a message when Node is not
  installed, and fails instead when the `CI` variable is set.
- The unit tests run under whichever Node a machine has, not only the Action's
  Node 24 runtime. Before Node 24 the timer behind `AbortSignal.timeout()` does not
  keep the event loop alive, and the timeout test's fetch holds nothing open, so
  the runner cancelled that test under Node 20 and 22. `main` had the defect; it
  showed on 2026-11-19 when `cargo test` first ran the suite on the hosted macOS
  and Windows runners, whose default Node was 22. The test now holds the loop open
  itself. The Action is unaffected: a real request holds a socket open.
