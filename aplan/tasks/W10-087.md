## Why

Audit finding E6 (medium, read from `release.yml`). The release jobs run
`verify → publish (crates.io) → github-release → binaries → action-smoke`:

- the irreversible step (crates.io) runs before the platform builds are known to succeed;
- `gh release create` publishes the release before any binary exists (`release.yml:176`), so
  for the length of the `binaries` job the Action's `latest` lookup resolves to a release
  whose assets return 404;
- `gh release upload … --clobber` (`release.yml:232`) lets a re-run replace an asset under a
  published checksum;
- the `.sha256` files prove integrity against the same origin only; there is no build
  provenance attestation, signature, or SBOM, and tags are unsigned;
- the job that holds the crates.io token compiles dependencies during `cargo publish`
  (reviewer suggestion: verify in an unprivileged job, publish with `--no-verify`).

## Why it is untestable

These are release-workflow changes proved by a release run.

## Edge cases

- Two crates are published, and that is not atomic: the library can be published
  and the CLI can fail. A second run publishes only what is missing, which
  `ci/publish.sh` already does.
- Draft release: the latest-release query ignores drafts, so the Action never
  sees a release without assets. A failed run leaves a draft behind; the next run
  reuses or replaces it.
- No `--clobber`. A second run compares the digest of an asset that exists and
  fails on a difference.
- Attestations need `id-token: write` and `attestations: write` in the build job,
  and only there.
- Verifying in the Action: `gh attestation verify` exists on hosted runners and
  may not exist in a container or on a self-hosted runner, and the Action has no
  npm dependencies. Decide what the Action does when it cannot verify: fail, or
  fall back to the checksum with a warning.
- `cargo publish --no-verify` skips the build in the job that holds the token.
  The unprivileged job that verified must have verified the same package, so
  compare the digests of the packaged crates.
- The order "build and smoke-test before publishing" means the smoke test runs
  binaries from workflow artifacts, not from a release.
- A release that has to be withdrawn: yanking leaves its tag, and
  `ci/buf-history-skip` is where the history gate is told.
- Signed tags and a software bill of materials: do them or record why not.

## Acceptance criteria

- [x] binaries are built and smoke-tested before anything is published
- [x] the GitHub release is created as a draft and published once every asset is attached;
      assets are never overwritten
- [x] each archive has a build provenance attestation that the Action verifies before
      running the binary
- [x] the publishing job runs no build scripts from dependencies
- [x] the checklist and `SECURITY.md` describe how to verify a download
