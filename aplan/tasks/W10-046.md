## Why

Audit finding A2 (critical). The `list<u8>` → `bytes` mapping is decided on the spelling of
the element type (`is_u8` at `proto.rs:1649` and `glue.rs:1281`), while the lockfile records
the resolved type. Two contracts with the same lockfile therefore have different encodings.

## Reproduction (re-run 2026-11-18)

```wit
package ex:b@0.1.0;
interface types {
  type byte = u8;
  record r { a: list<byte>, b: list<u8> }
}
```

`wire.lock` records `list<u8>` for both fields. `v0.proto` has `repeated uint32 a = 1;` and
`bytes b = 2;`. Respelling `a` as `list<u8>` in a later minor passes
`check --against` with an unchanged lockfile and changes the encoding of field 1.

Reviewer-run: the wrapper name `ListOfU8` is produced for both shapes, and mixing
`list<list<list<byte>>>` with the `u8` spelling produces glue that does not compile.

## Decision

Decided by the owner on 2026-11-19: aliases are resolved, and a list whose resolved
element type is `u8` is `bytes` in every emitter, whatever its spelling. The
lockfile already records the two spellings as one type, so this is a wire-format
correction and the changelog says so in its migration section. The only known
consumer (alint's proof crate) has no alias of `u8`.

## Edge cases

- Spellings that must all produce `bytes`: `list<u8>`, `list<byte>` with
  `type byte = u8`, a chain of aliases, a `use … as` rename of the alias, an alias
  declared in a dependency, and a named list (`type blob = list<byte>`).
- Positions: record field, parameter, function result, variant payload, option
  payload, result side, and list element (`list<list<byte>>` is `repeated bytes`),
  at top level and nested three deep.
- Only `u8` maps to `bytes`. `list<s8>` and a list of any other integer stay
  `repeated`.
- One wrapper per shape: today `ListOfU8` is produced for both spellings, and
  mixing them three levels deep produces glue that does not compile. After the fix
  there is one shape, and its wrapper name does not change for a contract that
  already used the `u8` spelling.
- JSON Schema has no byte-string form: section 10.2 maps every list to an array.
  The criterion for that emitter is that both spellings produce the same schema,
  not that the schema becomes base64.
- Plain Rust is `Vec<u8>` under either spelling, and `--serde` output does not
  change.
- Proto3 JSON changes with the field type: `bytes` is a base64 string, and
  `repeated uint32` is an array of numbers.
- The per-major proto file is shared by its minors, so the correction also changes
  how released minors of an affected contract are encoded.
- Mixed deployment: packed `repeated uint32` and `bytes` are both length-delimited,
  so a peer on the other encoding does not fail to decode. It reads the same bytes
  when every value is below 128 and different bytes otherwise. The migration note
  has to say this, because nothing will report it.
- How a consumer finds out whether it is affected: regenerate the proto output and
  look for a field that changed from `repeated uint32` to `bytes`.
- The history gate (`ci/check-buf-history.sh`) would report the type change for a
  fixture that had the alias spelling at an earlier release. No fixture has it;
  the new fixture is a new root, which the gate skips for releases before it.

## Acceptance criteria

- [x] every emitter decides the byte-list mapping on the resolved element type
- [x] a fixture with both spellings, at top level and nested three deep, generates identical
      field types and compiles against prost
- [x] the JSON Schema emitter produces one schema for both spellings
- [x] `emitters.md` states the rule, and the changelog's migration section names the
      affected shape, how to detect it, and what a mixed deployment reads
