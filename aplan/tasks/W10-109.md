## Why

Onboarding currently requires hand-authoring `wit/v0.1/contract.wit`, `witforge.toml`, and initial `wire.lock`; retiring a version requires hand-editing `wit/released`; and `new-version` can only bump the globally latest version, preventing maintenance minors (`v0.3`) once `v1.0` exists.

## Decision

- Add `witforge init [DIR] [--package <ns:name>] [--serde]` to scaffold a valid `wit/v0.1/contract.wit`, initial `wire.lock`, and `witforge.toml` (refusing to overwrite existing files).
- Add `witforge retire <WIT_DIR> [--released <PATH>] [--config/--project]` to validate release status, contiguous oldest-prefix ordering, and at-least-one-live-version, then atomically mark `<entry> retired` in the manifest.
- Add `--from <VERSION>` (e.g., `v0.2`) to `witforge new-version` so teams can cut a minor from an earlier major line.

## Acceptance criteria

- [x] `witforge init` creates a check-passing and generate-ready project without overwriting existing files
- [x] `witforge retire` atomically transitions a live released entry to `retired` and refuses non-prefix, unreleased, or last-live retirement
- [x] `witforge new-version --from v0.2` creates `v0.3` even when `v1.0` exists
- [x] CLI tests and `docs/guide/reference.md` cover all new commands and flags
