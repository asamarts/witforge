## Why

`witforge` already emits a deterministic, versioned JSON Contract IR (`witforge inspect --json`, `IR_VERSION = 1`). Providing a standardized process-based emitter plugin protocol (modeled after `protoc-gen-*`) lets external and community emitters target additional languages or frameworks (Kotlin, Swift, C++, Zig, Pydantic, internal SDKs) without forking `witforge`, while reusing `witforge`'s contract validation, lockfile enforcement, atomic file writes, symlink guards, ownership headers, and `--check` drift checks.

## Decision

Owner decision recorded on 2026-11-26 (unblocked ahead of `W10-002` as Stage 1 of the staged hybrid polyglot strategy):

- Standardize a versioned JSON-over-stdio process protocol (`protocol_version: 1`):
  - **Stdin request:** `protocol_version`, `ir_version`, validated `witforge inspect --json` IR payload (single-version or multi-version root), target `output_root`, normalized `options` map, and `contract_id` / ownership header metadata.
  - **Stdout response:** `protocol_version`, ordered list of emitted `{ path, content }` files (relative POSIX paths validated strictly inside `output_root`, no `..`, no absolute paths, LF-normalized) and optional structured diagnostics.
- Invoke plugins explicitly via `witforge plugin <name>` (resolving `witforge-gen-<name>` on `PATH` or an explicit `--plugin-bin` path) and optional `[project.<name>.plugins.<name>]` tables in `witforge.toml`.
- Keep plugin execution opt-in and strictly additive over the `0.x` library and CLI surface; never auto-discover or execute plugins unless explicitly requested.
- Enforce bounded I/O, deterministic sorting, atomic writes, contract-scoped ownership headers (or explicit opt-in comment prefix), symlink refusal, and `--check` drift detection inside `witforge` itself so plugins cannot bypass repository safety invariants.

## Edge cases

- Path traversal (`../`, absolute paths, Windows separators, duplicate output paths, or symlink targets) in a plugin response must be refused before any file is written.
- Non-zero exit codes, invalid JSON responses, mismatched `protocol_version`, or stderr output must surface as clear structured diagnostics with exit code `2` (operational error) or `1` (plugin contract violation).
- Plugins must work cross-platform (Linux, macOS, Windows) without assuming POSIX shell scripts.

## Acceptance criteria

- [ ] Publish the normative process-based emitter plugin protocol specification (`protocol_version = 1`) in `docs/design/plugins.md` (linked from `docs/design/emitters.md`)
- [ ] Implement the host-side plugin request/response serialization, strict output path/header validation, atomic write / `--check` integration, and bounded subprocess runner in `witforge` / `witforge-cli`
- [ ] Support `witforge plugin <name>` CLI flags (`--plugin-bin`, `--out`, `--check`, `--option k=v`) and `[project.<name>.plugins.<name>]` in `witforge.toml`
- [ ] Verify positive end-to-end execution, `--check` drift detection, and adversarial negative cases (path traversal, duplicate paths, invalid JSON, bad protocol version, non-zero exit) using a cross-platform test plugin in `cargo test`
- [ ] Document authoring and invoking third-party plugins in `docs/guide/generation.md` and `docs/guide/reference.md`
