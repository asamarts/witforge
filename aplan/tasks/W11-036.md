## Why

`diff` classifies a removed non-defaultable record field as source/API breaking but does not say that the generated new-to-old converter for the containing record returns `MissingMember` for every input. Reviewers supporting adjacent versions should see that operational consequence before release.

## Acceptance criteria

- [ ] derive conversion impact from the same defaultability rules used by adapter generation, without duplicating semantics
- [ ] report one deterministic note per affected type, naming the impossible direction and missing member
- [ ] expose the note in human, `diff --json`, JSON diagnostics, and SARIF output without changing existing compatibility counts or exit codes
- [ ] distinguish guaranteed failure from value-dependent `UnknownCase` paths
- [ ] preserve the declared 1.0 public API or use an additive API reviewed by the semver gate
- [ ] add behavioral tests for required removal, defaultable removal, rename, and multiple affected types
