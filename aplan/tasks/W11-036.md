## Why

`diff` classifies a removed non-defaultable record field as source/API breaking but does not say that the generated new-to-old converter for the containing record returns `MissingMember` for every input. Reviewers supporting adjacent versions should see that operational consequence before release.

## Acceptance criteria

- [x] derive conversion impact from the same defaultability rules used by adapter generation, without duplicating semantics
- [x] report one deterministic note per affected type, naming the impossible direction and missing member
- [x] expose the note in human, `diff --json`, JSON diagnostics, and SARIF output without changing existing compatibility counts or exit codes
- [x] distinguish guaranteed failure from value-dependent `UnknownCase` paths
- [x] preserve the declared 1.0 public API or use an additive API reviewed by the semver gate
- [x] add behavioral tests for required removal, defaultable removal, rename, and multiple affected types

## Verification

- `diff_reports_guaranteed_down_conversion_failures` covers required removal, defaultable
  removal, multiple affected types, human/JSON/JSON-diagnostics/SARIF output, unchanged counts,
  and `--check` exit behavior.
- `diff_reports_a_rename_as_a_missing_old_member_only` covers a rename and the value-dependent
  variant-case path.
- `cargo test --workspace --locked`, the MSRV 1.88 run, Clippy with `-D warnings`, rustdoc with
  `-D warnings`, and `ci/check-generated.sh` pass. The new public items are additive; hosted CI
  runs the semver gate.
