## Why

Audit finding D4 (high for adopters). `diff` reports an added required field and an added
enum case as `wire:compatible`, because no number changed meaning. The generated glue
nevertheless rejects the messages: a new reader's `from_proto` fails on an old message that
lacks the required field (`MissingField`), and an old reader fails on an enum value it does
not know (`UnknownEnumValue`). Two services at different contract versions therefore cannot
talk, and `diff --check` says the change is safe. Read from `emitters.md` sections 7 and 9 and
the generated error type; the cross-version decode was not run.

## Decision

Default chosen while documenting the task on 2026-11-19, not an owner decision:
the new view does not gate `diff --check` unless it is selected (`W10-085`).
Gating on it by default would turn a passing gate red for an added enum case.
Whether it joins the default set is decided at 1.0.

## Edge cases

- The finding was read from the specification and the generated error type; the
  decode across versions was not run. Running it is the first step, and the view
  describes what was observed.
- Each change kind in both directions: an added required field, an added
  `option` or `list` field, a removed field, an added and a removed enum case, an
  added and a removed variant case, an added flag, and an added and a removed
  function.
- Glue exists for the highest minor of a major only. The test generates glue from
  two roots, one that ends at the old minor and one that ends at the new.
- The view is about one major. Two majors have two proto packages.
- Binary encoding and proto3 JSON can differ, for example in how an unknown field
  is treated. Say which the view describes.
- The rules are those of the decode profile documented for non-Rust
  implementations, not only what the Rust glue happens to do.
- The JSON report gains fields and loses none. `diff.md` describes them.
- The view is distinct from the conversion notes: `convert.rs` converts values in
  one process, and this view is about two processes at two versions.

## Acceptance criteria

- [x] `diff` has a view that answers, per change, whether a new reader accepts old messages
      and whether an old reader accepts new messages under the generated glue's rules
- [x] `diff --check` can gate on it when it is selected, and does not by default
- [x] a test encodes with one version's glue and decodes with the other's for each change
      kind, and the view's verdict matches the observed result
- [x] the evolution guide explains the difference between wire identity and decode
      compatibility
