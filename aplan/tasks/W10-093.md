## Why

Audit finding D1 (high for the 1.0 design). The tool has no usable story for a breaking
change.

Re-run in the first audit pass: with `v0.2` and `v1.0` in one WIT root, `witforge rust`
refuses a retyped field, a kind change, and a required addition across the major boundary,
because conversion is generated between every adjacent pair of versions (`emitters.md`
section 9.1 includes the major boundary). A new major therefore cannot make the changes a
new major exists for. Putting the new major in a separate WIT root with separate output
directories works and is not documented.

Also: the freeze check forbids removing an entry from `released`, and the tool has no way to
retire a version, so every version ever released is generated forever; `diff` impact notes
are incomplete for a retype across a major; `witforge rust` has no option to skip conversion
generation; no user document describes starting a major.

## Reproduction (re-run 2026-11-19)

One WIT root with `v0.1`, `v0.2` (which adds an optional field), and a `v1.0`
locked with `--first`. The columns are exit statuses.

```text
change in v1.0                    rust  proto schema glue  diff  check v1.0
                                                                 --against v0.2
none (identical contract)          0     0     0     0     0     0
a required field removed           0     0     0     0     0     1
a field retyped (u32 to string)    1     0     0     0     0     1
a type changes kind                1     0     0     0     0     1
a required field added             1     0     0     0     0     0
a type renamed, used by a record   1     0     0     0     0     1
a dependency's record changed      1     1     1     1     1     (check v1.0: 0)
```

- When `rust` exits 1 it writes nothing, so there is no `v1_0.rs` either: the
  plain types of the new major are lost with the adapters.
- The identical contract gets adapters `v0_2_to_v1_0` and `v1_0_to_v0_2`.
- After a removed required field, the conversion from `v1.0` back to `v0.2`
  exists and always returns `MissingMember`.
- With a changed dependency the message is "dependency graph differs … every
  version in a generated WIT root must use an identical pinned dependency
  graph". A new major therefore cannot change, add, or upgrade a dependency at
  all inside one root.
- `check --against` across the major is not refused today (`W10-048`).
- Putting the new major in a WIT root of its own, with its own output
  directories, works for every row. It is not documented.

## Decision

Decided by the owner on 2026-11-19 (option A of three).

- Inside a major nothing changes: a change that cannot be converted is refused.
- Across a major boundary the generator never refuses. It generates the adapters
  for the types that still convert under the rules of `emitters.md` section 9,
  and omits the ones that do not. A type that contains an omitted type is omitted
  too. Omission is per direction.
- Every omission is listed, with its reason, in a comment block at the top of
  `convert.rs` and in `diff`.
- The plain types of every version are generated whether or not an adapter can
  be.
- Names stay identity across a major. A renamed type is a removal and an
  addition.
- The pinned-dependency-graph rule holds within a major, not across one.
- Retirement is a recorded state in `released`. The directory stays, stays
  frozen, and stops being generated. An entry is never deleted.
- The evolution guide gets a section on starting a new major.

Deferred: a hook through which a consumer supplies the conversions that were
omitted. It can be added later without breaking anyone, and its shape should
come from a consumer that has a real major. Until then the consumer writes those
conversions in its own code, next to the generated ones.

Rejected: refusing as today and documenting a separate root per major as the only
way. That keeps every version's types out of one module tree, and gives up the
adapters for the types that did not change, which are most of them.

What was looked at: Kubernetes `conversion-gen` generates the conversions it can
and leaves the rest to hand-written functions. Terraform's plugin protocols 5 and
6 are separate packages with a hand-written bridge. The recorded design of this
project (`overview.md` section 6.5, the alint plugin architecture) has the host
convert each supported version to the newest plain types, which needs the
adapters that still can be generated.

## Edge cases

- Omission per direction: after a required addition, old-to-new cannot default
  the field and is omitted, while new-to-old drops it and is generated.
- Transitive omission: a record with a field of an omitted type, a `list`,
  `option`, or `result` of one, and a variant with a case that carries one. The
  whole containing type is omitted, in that direction.
- Each row of the reproduction, with the reason that is listed: a retype, a kind
  change, a required addition, a changed payload presence, and a type that has no
  namesake in the other version.
- A foreign type converts across the major only when both majors pin the same
  version of its package.
- The comment block is sorted and deterministic, and `--check` covers it like the
  rest of the file.
- `diff --check` across a major boundary still exits 1 for a breaking change. A
  consumer that expects one does not gate on it.
- Dependencies per major. The dependency bindings are one surface per root today
  (`witforge_deps.rs`, and one proto file per dependency package and major). Two
  majors that pin two versions of one dependency package need two plain Rust
  modules for it. That layout is part of this task, and 1.0 freezes it. Inside
  one version directory two versions of a package stay refused (`W10-047`).
- The lockfile of a new major starts fresh with `--first` (`W10-048`). Its proto
  file and glue module are the new major's.
- Retirement syntax in `released`: a tool release that does not know it rejects
  the manifest as malformed. State the first release that reads it.
- The freeze check (`ci/check-release-freeze.sh`, `W10-083`) has to accept the
  one change of an entry from live to retired, and no other.
- Which versions can be retired: the oldest ones. Retiring `v0.2` between a live
  `v0.1` and `v0.3` would need an adapter between versions that are not
  neighbours; refuse it.
- What retirement removes from the output: the version's plain module and its
  adapters. Stale-file removal deletes them from a consumer's tree, which is the
  intent. The proto file of a major is built from its highest minor and keeps
  every reservation, so retiring a minor changes nothing on the wire.
- Retiring every version of a major stops its proto file and glue module.
- A root per major stays supported and is documented as the alternative.
- Trait adapters between versions are `W11-038`.

## Acceptance criteria

- [x] the specification defines what a major boundary allows and what is generated across it
- [x] `witforge rust` succeeds on a root with a breaking `v1.0` after `v0.x` for every row of
      the reproduction, writes the plain types of every version, and the result compiles
- [x] a test asserts the adapters that are generated and the omissions that are listed, per
      direction, and that a change inside a major is still refused
- [x] a new major can change, add, and upgrade dependencies, with a compile test
- [x] the oldest versions of a root can be retired in `released`; the freeze check accepts
      that change and no other, and a retired version is no longer generated
- [x] `diff` across a major reports every conversion that needs consumer code, per
      direction, and `convert.rs` lists the same set
- [x] the evolution guide has a "starting a new major" section, which also describes a root
      per major
