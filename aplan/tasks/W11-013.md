## Why

Zed is a production WIT-first extension ecosystem with explicit API-version directories and compiled-component compatibility. Its resource-heavy host API likely makes it prior art rather than a 0.4 consumer.

## Acceptance criteria

- [ ] pin the reviewed extension API versions, WIT sources, SDK generation, archive metadata, compatibility policy, and frozen-component tests
- [ ] identify any value-only sub-contracts with a real need for protobuf, schema, lockfile, diff, or version conversion
- [ ] classify resources, borrows, world functions, host callbacks, process execution, and state against witforge 0.4
- [ ] compare Zed's version-directory and compatibility practices with witforge and extract lessons without claiming adoption value
- [ ] state whether witforge solves any current objective problem or whether the correct conclusion is non-fit
- [ ] record project-side and witforge-side gaps and a go/no-go recommendation
- [ ] apply the external-adoption protocol: label material claims, decide all four gates, complete the six-dimension matrix, state the falsifier, and choose contact, defer, or no-contact
- [ ] record the canonical outreach path and policy: GitHub Discussion before any issue or code, especially for Extension API changes

## Why it is untestable

This is a comparative external extension-API review.
