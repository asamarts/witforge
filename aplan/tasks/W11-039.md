## Why

The emitted `.proto` files currently carry no language-specific file options (`go_package`, `java_package`, `java_multiple_files`, `java_outer_classname`, `csharp_namespace`). Go consumers cannot compile emitted `.proto` files with `protoc-gen-go` without per-file `M` mapping flags, and Java/C# consumers get default package/namespace placement instead of idiomatic module layout. Supporting opt-in, strictly non-wire file options is the first step of Stage 1 polyglot readiness ahead of `W11-034` and `M-p13`.

## Decision

Owner decision recorded on 2026-11-26 (unblocked ahead of `W10-001` as strictly additive `0.x` polyglot Stage 1 work):

- Implement opt-in protobuf file options via CLI flags and `[project.<name>.proto]` in `witforge.toml` (`go_package`, `java_package`, `java_multiple_files`, `java_outer_classname`, `csharp_namespace`, plus safe prefix derivation for multi-major and `deps/` `.proto` files).
- Keep default `.proto` output byte-for-byte unchanged when no file options are configured.
- File options never affect wire identity, lockfile keys, `wire.lock`, or compatibility verdicts.
- Validate option values against safe protobuf string-literal / identifier rules and escape cleanly, refusing control characters or malformed values with structured diagnostics.

## Edge cases

- Multiple majors (`v1`, `v2`) and `deps/` dependency `.proto` files need deterministic, collision-free per-file values derived cleanly from a configured base prefix (or explicit per-package overrides).
- File options are strictly non-wire: `wire.lock` and `witforge diff --check=wire,decode` are unaffected.
- `buf breaking` with default rules flags changed file options once if a consumer opts in later; document that clearly in `docs/guide/non-rust.md`.
- Existing fixtures emit zero file options so `ci/check-buf-history.sh` and existing golden tests remain unchanged.
