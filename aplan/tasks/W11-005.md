## Why

wit-bindgen is the canonical guest Component Model binding generator and consumes the same WIT source language. witforge must state where the tools complement one another, avoid reimplementing Canonical ABI work, and copy proven generator practices only where they serve runtime-independent contracts.

## Acceptance criteria

- [ ] compare missions and trust boundaries: guest Component Model bindings and Canonical ABI lift/lower versus plain Rust, protobuf, schema, lockfile, diff, and version conversion
- [ ] compare WIT/package/world resolution, supported constructs, dependency handling, feature gates, naming, collisions, diagnostics, and generated-layout ownership
- [ ] compare Rust ergonomics including owning/borrowing modes, interface/type remapping, selective generation, stubs, derives and targeted attributes, raw strings, std/no_std concerns, and debugging generated output
- [ ] compare compatibility and release policies, including wit-bindgen's unstable CLI and generated API versus witforge's 1.0 commitments
- [ ] compare codegen golden and runtime conformance testing across languages and identify practices witforge should adopt
- [ ] identify overlap that witforge should explicitly decline, especially Component Model ABI shims, guest export machinery, and runtime execution
- [ ] evaluate the proposed bridge between witforge plain values and wit-bindgen/Wasmtime-generated values, including API coupling and avoidable allocation
- [ ] produce a prioritized improvement list with evidence, explicit non-goals, and triggers for separately scoped implementation tasks; do not implement speculative parity

## Why it is untestable

This is a comparative architecture and product-boundary review. Accepted implementation work must receive its own tested task.
