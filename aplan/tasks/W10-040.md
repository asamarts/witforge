## Why

Audit finding E2 (high). `ci/check-version-references.sh:61-62` (added by `W10-032` after
0.5.0) requires `ci.yml`'s `asamarts/witforge@vX` reference and `version: X` input to equal
the workspace version, and `ci/check-release.sh:38` runs it in the `generated` job. On a
release-preparation commit for the next version either:

- `ci.yml` still names the previous release and `generated` fails, or
- `ci.yml` names the new version, and the `published-action` job cannot resolve a tag that
  does not exist yet while the local Action smoke gets a 404 for its assets.

Both jobs are in `ci ok`'s `needs`, and `release.yml` refuses to publish without a successful
`ci ok` at the tag commit. `ci/release-checklist.md:123-124` still describes bumping the pin
after the release, which the new check forbids.

Verified by reading the scripts and workflow; the reviewer also simulated a 0.6.0 preparation
tree and got `.github/workflows/ci.yml:129: Action reference names 0.5.0; expected 0.6.0`.

## Acceptance criteria

- [x] the published-Action pin in `ci.yml` is checked against the latest *published* release,
      not the workspace version, or is exempt on a release-preparation commit by an explicit
      rule that the script tests
- [x] the local Action smoke does not need release assets of an unreleased version
- [x] `ci/test-release-version.sh` covers a release-preparation tree
- [x] `ci/release-checklist.md` describes the order that the scripts enforce
- [x] the usage line of `ci/check-version-references.sh` no longer marks `VERSION` optional

## Why it is untestable

The change is shell and workflow logic exercised by `ci/test-release-version.sh` and hosted
CI, not by a configured cargo runner.
