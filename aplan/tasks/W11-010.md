## Why

Pact already operates a protobuf/gRPC process-plugin system and has a draft proposal mapping it to WIT Component Model plugins. This directly tests witforge's multi-transport thesis, but maps, callbacks, dynamic values, and service semantics may make it a design partner rather than a 0.4 adopter.

## Acceptance criteria

- [ ] pin the reviewed proposal, branch/POC, protobuf contract, Rust driver, and current plugin lifecycle sources
- [ ] determine the current status and ownership of the Wasm proposal instead of assuming the draft is active
- [ ] map gRPC services/messages to proposed WIT calls and identify where stable wire numbers, plain Rust values, schemas, or version conversion solve a present problem
- [ ] classify maps, tuples, dynamic JSON, callbacks, services, async behavior, and plugin lifecycle against witforge 0.4
- [ ] evaluate bounded message sub-contracts separately from generating gRPC services or runtime framing, which witforge does not provide
- [ ] state concrete gaps and the questions that Pact maintainers must answer before any integration
- [ ] record a go/no-go recommendation and migration risk
- [ ] record the canonical outreach path: comment on the existing Wasm-plugin GitHub Discussion #85, or open a new Discussion only if that thread is closed or superseded

## Why it is untestable

This task investigates an external draft architecture and records design evidence.
