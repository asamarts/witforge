## Why

Audit finding C1 (high, re-run in the first audit pass). The model orders interfaces and
types by source span offset (`model.rs:526-565`), and wit-parser assigns offsets in the order
`Resolve::push_dir` enumerates the directory (`lib.rs:126-128`; wit-parser `ast.rs:1851`
reads the directory unsorted). For a version directory with more than one `.wit` file:

- generated output follows `ls -U` order;
- one contract with different file names produces different bytes.

`emitters.md` promises deterministic output. The difference between two machines is inferred
from how ext4 hashes directory entries per file system; it was not demonstrated on a second
file system. Single-file directories (all fixtures, both examples, and alint) are unaffected,
which is why `--check` has not failed in CI.

## Edge cases

- The order is by file name as bytes, not by locale, and then by position inside
  a file. `model.md` states it.
- Dependency packages under `deps/`, and the files inside each, are ordered by the
  same rule.
- Wire numbers cannot change: a parent's members are in one file, numbers are per
  parent, and method ids are per interface. Only the order of interfaces and types
  in the output moves. A test asserts that the lockfile of a multi-file contract
  is unchanged by the fix.
- Renaming a file can now change the output order, deterministically. The
  documentation says so.
- A package header in only one of the files, and an interface declared in one
  file and used in another.
- File names that differ only in letter case, and non-ASCII names, whose bytes
  differ between file systems. Recommend ASCII names in the documentation.
- The test cannot make a directory enumerate in a chosen order portably. Test the
  ordering function with a shuffled list, and add an integration test whose files
  are created in reverse name order.
- If `Resolve::push_dir` cannot be told the order, the files are parsed
  separately in sorted order. Check that source positions survive, because
  `W10-080` needs them.
- The per-version modules of a released multi-file contract change once. That is
  a migration entry; single-file contracts are unaffected.

## Acceptance criteria

- [x] a test generates one multi-file contract from two directories whose enumeration orders
      differ and gets identical bytes
- [x] the changelog says that output of an existing multi-file contract can change once
