## Why

`main` after 0.7.0 contains the strictly additive Tier 1 feature wave and five rounds of
adversarial audit hardening (`W10-115`–`W10-121`, `W10-122`, `W10-124`, `W10-125`, `W10-126`): lifecycle CLI
(`init`, `retire`, `new-version --from`/`--released`), versioned JSON contract IR (`inspect`),
opt-in `no_std` + `alloc` Rust/convert/glue output, the optional `witforge-build` helper crate,
JSON Schema Draft 2020-12 and member descriptions, static `musl` Linux release archives alongside
`gnu`, and GitHub Action shorthand inputs and default `github-token`.

## Why it is untestable

Publication is proved by the exact-commit `ci ok` result, the release workflow, install and
attestation checks, and the published crates/archives rather than by a repository test that
could fail if this task were reverted.

## Edge cases

- The release-preparation commit moves workspace crates, `witforge-cli`'s `witforge` dependency,
  `Cargo.lock`, `fuzz/Cargo.lock`, `CHANGELOG.md`, `README.md`, `crates/witforge-build/README.md`,
  documentation, and issue template versions to `0.8.0`, while leaving `.github/workflows/ci.yml`
  pinned to `0.7.0` until `v0.8.0` is tagged and published.
- Because `witforge-build` is a brand-new workspace crate not yet on crates.io, the repository
  owner must perform the one-time crates.io bootstrap (`cargo publish --locked -p witforge-build`
  with a short-lived `publish-new` token, followed by configuring Trusted Publishing on crates.io
  for `asamarts/witforge` / `release.yml` / environment `release` and revoking the token) AFTER
  exact-commit `ci ok` is green and BEFORE pushing tag `v0.8.0`.
- After `release.yml` publishes `v0.8.0`, record the release commit, CI run, and release run in
  `CHANGELOG.md` and `ci/release-checklist.md`, bump `.github/workflows/ci.yml` to `0.8.0`, and
  close this task.
