## Why

Lix ships a WIT Component Model file-plugin API, explicit compatibility policy, and frozen compiled fixtures across Rust and JavaScript hosts. It may teach witforge more than it needs witforge unless a separate wire/schema projection exists.

## Acceptance criteria

- [ ] pin the current WIT API, Rust and JavaScript hosts, plugin packages, compatibility policy, frozen archive tests, and superseded RFCs
- [ ] identify whether Lix maintains any second semantic contract or stable wire/schema surface that witforge could generate
- [ ] classify its resources, state, database/file operations, and value contracts against witforge 0.4
- [ ] compare frozen-binary compatibility and independent API versioning with witforge's conformance and version-tree model
- [ ] state objective current benefits or a clear non-fit, exact gaps, and migration cost
- [ ] apply the external-adoption protocol: label material claims, decide all four gates, complete the six-dimension matrix, state the falsifier, and choose contact, defer, or no-contact
- [ ] record the canonical outreach path: Lix Discord for design discovery, followed by a GitHub issue only if maintainers request durable tracking

## Why it is untestable

This is an external compatibility-practice and adoption-fit review.
