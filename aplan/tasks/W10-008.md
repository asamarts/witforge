## Why

The public API inventory lists generated `GlueError` as a library item, semver compatibility is
not a continuing gate, the protobuf check generates both sides with the candidate binary, tag
publication does not require `ci ok` for the exact commit, and the yanked-crate policy is weaker
than its documentation.

## Why it is untestable

These are CI and release-policy gates over GitHub Actions, crates.io baselines, buf, and
cargo-deny configuration. Reverting them cannot make a configured cargo test fail; actionlint,
shellcheck, the compatibility commands, and the hosted release workflow are their direct proof.

## Acceptance criteria

- [ ] the public API inventory distinguishes library items from generated output
- [ ] the release gate runs cargo-semver-checks against the 0.4.1 baseline with breaking changes
      denied for the 1.0 candidate
- [ ] protobuf release compatibility compares a historical release generator with the candidate
      across the released and dependency fixtures
- [ ] a tag publish requires successful `ci ok` for the exact commit
- [ ] the security support statement covers 1.x and cargo-deny refuses yanked crates
- [ ] release criteria and checklist name the exact commands and evidence
