## Why

loadr exposes bounded Component Model extractor/assertion plugins and separate native plugin mechanisms. It may benefit from contract generation, but the current transports do not obviously share one semantic interface and the WIT uses unsupported tuples.

## Acceptance criteria

- [ ] pin the reviewed commit/release and verify project maturity, license, plugin implementation status, and maintenance activity rather than relying on documentation claims
- [ ] map Wasm and native plugin kinds, WIT contracts, SDK types, configuration schemas, and any protobuf/gRPC surfaces
- [ ] identify objectively duplicated contracts or evolution risks, if any
- [ ] classify tuples, JSON configuration, headers, lifecycle, and long-running plugin kinds against witforge 0.4
- [ ] evaluate whether a record-pair remodel and generated outputs create net value or merely replace simpler current bindings
- [ ] record smallest useful slice, missing witforge features, upstream changes, and go/no-go recommendation
- [ ] apply the external-adoption protocol: label material claims, decide all four gates, complete the six-dimension matrix, state the falsifier, and choose contact, defer, or no-contact
- [ ] record the canonical outreach path: a GitHub issue because no Discussions or contribution guide is published

## Why it is untestable

This is an external-product maturity and contract-fit investigation.

## Migration disposition

Detailed candidate research and outreach preparation moved to the private `asamarts/witforge-research` repository on 2026-11-11. This public research task is dropped; `W10-001` still owns witforge's independent-adoption release gate.
