## Why

`GeneratedFiles::write` removes stale generated files and then calls `fs::write` directly
for every expected file. A crash or write failure can leave a truncated generated file, and
stale files may already be gone. A truncated file that lacks the ownership header can then
block the next generation run.

## Acceptance criteria

- [x] each expected file is staged and renamed atomically, so a failed write never leaves a
      partial generated file
- [x] stale generated files are removed only after all expected writes succeed
- [x] existing ownership, symlink, non-regular-file, and stale-file checks are preserved
- [x] a failure-path test (for example an unwritable expected file on Unix) proves previous
      output remains intact
- [x] `ci/check-generated.sh` and the full workspace suite pass

## Verification

- `emit::output::tests::write_atomic_replaces_files_and_cleans_up_a_failed_replacement`
- `generation_leaves_previous_output_when_a_write_fails`
- `cargo test --workspace --locked`, MSRV 1.88, Clippy, rustdoc, and `ci/check-generated.sh` pass.
