## Why

A thin component/process/native conformance kit is justified only if independent projects repeat mechanics that existing runtimes do not already provide.

## Acceptance criteria

- [ ] compare repeated adopter mechanics with direct Wasmtime, wit-bindgen, Extism, wasm-link, wRPC, and existing application SDKs
- [ ] require evidence from at least two real applications before extracting shared runtime or transport code
- [ ] evaluate semantic fixture reuse, version mismatch, malformed output, limits, traps/crashes, and process framing without absorbing application policy
- [ ] measure or explicitly defer the generated bridge between witforge and Component Model binding types
- [ ] decide build, defer, or decline; if building, define a separate package/repository boundary and create fully scoped tested tasks
- [ ] do not turn W11-001's witforge-emitter protocol into an application plugin framework

## Why it is untestable

This is a post-adoption architecture decision; accepted implementation receives tested tasks.
