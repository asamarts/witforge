## Why

Audit finding C2 (high, re-run 2026-11-18). The CLI prints with `println!`
(`diagnostics.rs:89`, `103`, `107`; `main.rs:723`, `729`), which panics when stdout is
closed, and `lock` prints its `added …` lines before `lock.write_atomic` (`main.rs:567-599`).

```text
witforge diff wit/v0.1 wit/v0.2 | head -0         exit 101, panic message      (5 of 5 runs)
witforge lock wit/v0.1 --first > /dev/full        exit 101, no wire.lock written
witforge lock wit/v0.1 --first | head -1          400-member contract: no wire.lock in 30 of
                                                  30 runs; 6-member contract: 0 of 30
```

A script that pipes `lock` through `head` or `grep -q` gets no lockfile and, without
`pipefail`, no failure.

## Edge cases

- The three cases of the reproduction: a reader that takes nothing (`head -0`), a
  reader that leaves early (`head -1` on long output), and a full device.
- The exit status is the result of the work, not of the printing. `diff --check`
  into `grep -q` exits 1 for a breaking change even though the reader left, and
  `check` into a closed pipe keeps its 0 or 1.
- A write error that is not a closed pipe (a full device) ends with exit 2 after
  the work is done, and with a message on stderr when stderr is usable.
- Standard error closed as well.
- Rust ignores SIGPIPE, so a closed pipe arrives as an error from the write.
  Restoring the default signal would kill the process at an arbitrary point, and
  is not the fix.
- Windows reports a closed pipe differently; the handling is by error kind.
- `lock --first`, `lock --against`, and the default `lock` all write before they
  print.
- Generators write their files before they print the summary.
- JSON and SARIF output cut short by a closed pipe is not an error. Cut short by
  a full device, it is exit 2.
- The tests close the reading end of a pipe from Rust, with no shell. The
  full-device test is Linux only.

## Acceptance criteria

- [ ] `lock` writes `wire.lock` before it prints anything
- [ ] a failed write to stdout ends the process with a defined exit code and no panic;
      a closed pipe is not an error for a command whose work is already done
- [ ] tests cover a closed pipe and a full device for `lock`, `diff`, and a generator
