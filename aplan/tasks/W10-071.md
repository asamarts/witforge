## Why

Audit finding B14 (medium, reviewer-run). With `--serde`:

- `option<option<T>>`: `Some(None)` serializes as `null` and deserializes as `None`;
- a NaN float serializes as `null` and then fails to deserialize;
- the Serde fixture has no nested option or result although the specification says the
  round trip covers them;
- the JSON names are documented only in general. The README ("Important JSON boundary") and
  `docs/guide/json-projections.md` say that Serde uses the Rust spelling and that the Serde
  and JSON Schema surfaces of one contract differ. Neither they nor `emitters.md` give the
  cases a consumer has to know: a field named `self` is keyed `self_`, enum cases are
  `"DoneNow"`, results are `{"Ok": …}` where the JSON Schema emitter describes `{"ok": …}`.

## Decision

Default chosen while documenting the task on 2026-11-19, not an owner decision.

`--serde` adds plain derives, and a derive does not choose a format. Both losses
in the finding belong to JSON: a format that tags options round-trips
`Some(None)`, and a binary format round-trips NaN. Refusing `--serde` for a
contract with a nested option would therefore break consumers who use another
format, and generating custom serializers would decide the JSON representation
that `W11-035` is meant to design. So:

- the derives stay as they are;
- `emitters.md` states that the derives are format-independent, and names the two
  values that `serde_json` does not round-trip;
- a test pins that behaviour, so a change is noticed;
- the names stay the Rust spelling and differ from the JSON Schema names by
  design. Aligning them is `W11-035`.

The alternative, refusing `--serde` when a contract has `option<option<T>>`,
stays available and is compatible later.

## Edge cases

- Nested options: `option<option<T>>`, three levels, inside a list, and through an
  alias (`option<maybe>` with `type maybe = option<u32>`).
- Floats: NaN, both infinities, and negative zero, as a field, a list element, and
  an option payload.
- 64-bit integers above 2^53 are written exactly; a JavaScript reader loses
  precision. Same caveat as `W10-070`.
- Keys to specify: a field whose Rust name is escaped (`self` is `self_`; a raw
  identifier such as `r#type` is keyed `type`), enum cases (`"DoneNow"`), variant
  cases with and without a payload, flags, and results (`{"Ok": …}`,
  `{"Err": …}`, and a side without a payload).
- A byte list is an array of numbers, not base64.
- The keys change with the identifiers of `W10-059` (`URL` becomes `url`); the
  migration section says so.
- Reading: an absent `option` field is `None` under a derive, while the JSON
  Schema requires the property. An unknown field is ignored under a derive, while
  the schema rejects it. Both differences are stated.
- Across versions: a document written by `v0.1` and read as `v0.2` gets `None`
  for an added `option` field and an error for an added `list` field, unlike the
  generated conversions, which default both. Specify it.
- The Serde fixture gains a nested option and a result, which the specification
  says the round trip covers.

## Acceptance criteria

- [ ] `emitters.md` states that the derives are format-independent and names what
      `serde_json` does not round-trip (a nested option's `Some(None)`, a non-finite
      float); a test pins both, and the fixture has a nested option and a result
- [ ] field, case, and result keys are specified in `emitters.md`, with each difference
      from the JSON Schema names and from the schema's reading rules
