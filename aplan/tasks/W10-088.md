## Why

Audit finding E7 (medium to low).

- `ci.yml` uses `concurrency: group: ci-${{ github.ref }}` with `cancel-in-progress` only
  for pull requests. GitHub still keeps at most one *pending* run per group, so a push to
  `main` while a run is in progress and another is queued cancels the queued one. The
  comment "every commit on main gets a result" is not true, and the release workflow needs
  `ci ok` on the tag commit. Five empty commits since `v0.5.0` ("retry CI after macOS …
  queue") re-triggered runs that never produced a result; whether those runs were cancelled
  while pending or timed out waiting for a macOS runner was not determined.
- No workflow runs on a schedule, so advisories, toolchain drift, and the fuzz targets are
  only exercised by a push.
- The toolchain is floating `stable`; a new Clippy lint breaks `main` without a change
  (commit `adba55d` was such a fix).
- Leftovers of the retired self-hosted runner remain (`ci.yml:26-34`, `ci/Containerfile`).
- `ci/deny.toml` allows `BSD-2-Clause`, `Unlicense`, and `LGPL-2.1-or-later`, which no
  dependency uses.
- Scripts default their scratch to `/tmp` (`ci/test-publish.sh:18`,
  `ci/check-generated.sh:10`, `ci/test-release-freeze.sh:14`, `ci/release-asset.sh:38`), and
  `ci/test-release-version.sh:6` ignores `TMPDIR`.
- The benchmark ceilings are 5 s and 15 s for work measured at about 1 ms and 270 ms.

## Why it is untestable

These are workflow and script changes; no cargo test fails if they are reverted.

## Decision

Default chosen while documenting the task on 2026-11-19, not an owner decision.

The benchmark tests keep a ceiling, set to ten times the value measured on a
hosted runner. A ceiling of 5 s for work that takes 1 ms guards nothing; without
any ceiling the test would only show that the code runs.

## Edge cases

- Concurrency: a group per commit for pushes to `main`; pull requests keep one
  group per ref with cancellation. Tag pushes and manual runs are checked too.
- Find out why the five retried runs produced no result (cancelled while pending,
  or timed out in the macOS queue) from the runs' metadata before changing
  anything, since the two causes have different fixes.
- A scheduled workflow runs on the default branch only, and GitHub disables it
  after sixty days without repository activity. Say who is told when it fails.
- Pinning the lint toolchain must not pin the toolchain contributors build with,
  and must leave the MSRV job on 1.88. The scheduled run builds on current
  stable and reports; it does not gate `main`.
- Runner leftovers include the `runs-on` expression of the `buf` job, which still
  selects a self-hosted runner when the repository is private. `AGENTS.md` forbids
  attaching one to this repository.
- Scratch directories: with `TMPDIR` unset the default is `$HOME/.tmp`, as in
  `ci/check-buf.sh`, not `/tmp`.
- Benchmark ceilings on hosted runners need headroom for a noisy neighbour; one
  order of magnitude is the bound in the criterion.
- `ci/check-buf-history.sh` installs every release on every run: eleven today, about
  half a minute each on a hosted runner, and one more per release (code review,
  2026-11-19). Cache the baseline binaries in the manual `buf` job. Do not cache
  them in `release.yml`: a poisoned cache there could pass the gate.
- Every new job is in the `needs` of `ci ok`.

## Acceptance criteria

- [x] runs on `main` are grouped per commit, so none is cancelled while pending
- [x] a weekly scheduled run covers the security audit, the fuzz smoke, and a build on the
      current stable toolchain
- [x] the lint toolchain is pinned and updated by a reviewed change
- [x] runner leftovers and unused licence allowances are removed
- [x] every script takes its scratch directory from `TMPDIR`
- [x] benchmark ceilings are within one order of magnitude of the values measured on a
      hosted runner, and the measured values are recorded beside them
- [x] the manual `buf` job reuses baseline binaries between runs, and `release.yml` does
      not
