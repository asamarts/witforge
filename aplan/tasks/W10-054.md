## Why

Audit finding A11 (medium, re-run 2026-11-18). In an unreleased `v0.2` whose baseline `v0.1`
declares `record r { a: u32, b: u32 }`: remove `b`, run `lock --against`, then restore `b`
and run `lock --against` again. The second run exits 1 with "its name and number 2 stay
reserved" (`lock.rs:523-527`), although `b = 2` is live in the released baseline and nothing
with the removal was ever released. The only way back is to edit `wire.lock` by hand or copy
it again and lose the other draft entries.

## Acceptance criteria

- [ ] a member reserved only in the draft lockfile, and live with the same number, kind, and
      type in the `--against` baseline, can be reintroduced by `lock --against`
- [ ] a member reserved in the baseline still cannot be reintroduced
- [ ] `lockfile.md` describes the rule and tests cover both cases
