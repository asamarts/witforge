## Why

Audit finding A11 (medium, re-run 2026-11-18). In an unreleased `v0.2` whose baseline `v0.1`
declares `record r { a: u32, b: u32 }`: remove `b`, run `lock --against`, then restore `b`
and run `lock --against` again. The second run exits 1 with "its name and number 2 stay
reserved" (`lock.rs:523-527`), although `b = 2` is live in the released baseline and nothing
with the removal was ever released. The only way back is to edit `wire.lock` by hand or copy
it again and lose the other draft entries.

## Edge cases

- Restored with the baseline's number, kind, and type: allowed. The lockfile is
  then byte-identical to one in which the member was never removed.
- Restored with another type or kind: refused as a change of a released member.
- Reserved in the baseline: still refused, with today's message.
- A member the draft added, removed, and added again was never released. Its entry
  is dropped and the new one may get another number.
- A draft member added while the released one was removed does not take its
  number, because reserved numbers count when a new number is chosen. The restore
  therefore never meets a number conflict; assert it.
- Without `--against` the tool has no baseline and cannot know that the removal
  was a draft. The default-mode message points at `--against`.
- The order section after the restore puts the member where the baseline's order
  of common members requires it.
- The same rule for a field, a variant case, an enum case, a flag, a parameter,
  and a function.
- A whole type or interface removed in the draft and restored.

## Acceptance criteria

- [x] a member reserved only in the draft lockfile, and live with the same number, kind, and
      type in the `--against` baseline, can be reintroduced by `lock --against`
- [x] a member reserved in the baseline still cannot be reintroduced
- [x] `lockfile.md` describes the rule and tests cover both cases
