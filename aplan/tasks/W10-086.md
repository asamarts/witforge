## Why

Audit findings E5 and F5 (medium).

- `resolveVersion('', ref)` returns `latest` for any ref that is not a version tag
  (`action/index.js:29-38`, `149-150`). A consumer who pins the Action to a commit SHA, as
  GitHub's hardening guide recommends, runs whichever binary is newest that day: the pin
  fixes the JavaScript and not the tool.
- The Action cannot run `check --against`, the release-freeze check, or `--format sarif`,
  and emits no workflow annotations. The documented snippet therefore cannot express the
  check the evolution guide asks for.
- The snippet that was documented until 2026-11-19 (`diff-old: wit/v0.1`,
  `diff-new: wit/v0.2`) fails on this repository's own `examples/evolved`, because
  `diff-check` defaults to true and that example has a source-breaking change. The
  snippets were replaced under `W10-039`; a snippet that uses the inputs and passes
  on the example is still missing.
- `diff-check`, `version`, `project`, and `github-token` are documented only in
  `docs/design/action.md`, which `docs/_config.yml` excludes from the site.
- The checked-out Action smoke in CI installs a published binary (`version:` names a release),
  so an input that needs a newer CLI cannot be exercised before that CLI is released.
- The platform map has no `linux/arm64`; the temporary directory is never removed; downloads
  are not retried; inputs are validated after the download.

## Decision

Default chosen while documenting the task on 2026-11-19, not an owner decision: a
ref that is not a release tag installs the version recorded in the Action's own
tree at that ref, which is the workspace version in `Cargo.toml`. When that
version has no published assets (a release-preparation commit, or a branch ahead
of a release), the step fails and names the `version` input. It never falls back
to `latest`. An explicit `version: latest` keeps working.

Changed under `W10-039` on 2026-11-19, so no longer part of this task: the
documented snippets run `witforge diff` as a separate reporting step and no
longer gate by accident, and `github-token` is sent only to the latest-release
query.

## Edge cases

- Refs: a release tag, a full commit SHA, a branch, and the empty ref of a local
  `uses: ./`.
- Validation before any download: one of `diff-old` and `diff-new` without the
  other, an unknown generator, generators without a configuration, and a
  malformed `version`.
- `against` has to say which `check` entry it belongs to, since `check` takes
  several directories. Decide the form before adding the input.
- The freeze check (`W10-083`) needs the full history. The Action cannot fetch
  it; it fails with the `fetch-depth: 0` hint.
- Reports: uploading SARIF is a separate step with `security-events: write` and
  is not available to a pull request from a fork. Workflow annotations are the
  form that always works, and they need positions (`W10-080`).
- The binary has to stay on `PATH` for later steps, so the Action cannot delete
  its directory when it ends. Remove the archive and checksum, and keep the
  binary under the runner's temporary directory, which the runner clears.
- Retries: a bounded number, for network errors and server errors only. A
  checksum mismatch is never retried.
- Running against a binary built from the same commit needs a way to skip the
  installation. If that is an input, it is public and documented.
- The CI smoke of the gate asserts which command failed. Today it accepts any
  failure of the step, so a failed download would also satisfy it (code review,
  2026-11-19). An output that names the failed command is one way.
- `linux/arm64` joins the platform map with `W10-090`. An unsupported platform
  names itself in the error.
- The public page documents every input with two snippets: one that passes on
  `examples/evolved`, and one that shows a failing gate.

## Acceptance criteria

- [ ] a ref that is not a release tag installs the version recorded in the Action's own tree
      at that ref; when that version has no published assets the step fails and names
      `version`; `latest` is installed only when it is asked for
- [ ] inputs exist for `against`, the freeze check, and the report format; a failing check
      produces workflow annotations, and the guide shows the separate step that uploads
      the SARIF file
- [ ] inputs are validated before anything is downloaded; the scratch directory is removed
- [ ] the checked-out Action can be smoke-tested in CI against the binary built from the same
      commit
- [ ] every input is documented on the public site, with a snippet that passes on
      `examples/evolved` and one that shows a failing gate
- [ ] `node --test action/test.js` covers version resolution for a tag, a SHA, and a branch
- [ ] the CI smoke of the diff gate asserts that the step failed in `witforge diff`, not
      while installing
