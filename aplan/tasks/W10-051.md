## Why

Audit finding A8 (medium). `lockfile.md` section 5 and `model.md` section 4 say an alias is
expanded to its target in a canonical type string. For a type imported from a dependency the
lockfile records the alias name instead (`model.rs:421-423`):

```text
ex:root/api/r.c = 1 field ex:shared/types/id        # type id = u64 in the dependency
ex:root/api/r.c = 1 field ex:shared/types/items     # type items = list<item>
```

Re-run 2026-11-18: with `v0.1` released and the dependency's `type id = u64` changed to
`type id = string` in `v0.2/deps`, `lock --against` and `check --against` exit 0 and the
lockfile line is unchanged. The change is caught later and elsewhere: `proto` and a root
`diff` exit 1 with "dependency graph differs: dependency type `ex:shared/types/id` shape
changes; every version in a generated WIT root must use an identical pinned dependency
graph". So the wire is protected, but by a rule the lockfile specification does not state,
and `check --against`, the documented gate, passes a contract the generators refuse.

## Decision

Decided by the owner on 2026-11-19: the recorded lockfile form stays. A foreign
alias keeps its alias name in the canonical type string, because expanding it
would change the type column of lockfiles that are already released and frozen.
The specification is corrected to describe that form, and `check --against` runs
the pinned-dependency-graph comparison that the generators run, so the lockfile
gate and the generators agree.

## Edge cases

- What is recorded for each foreign shape, stated in the specification and
  asserted by a test: an alias of a primitive (`ex:shared/types/id`), an alias of a
  named type, a named `list`, `option`, or `result`, and a chain of aliases that
  crosses the package boundary. Local aliases keep expanding.
- `check --against` receives a lockfile path, and the comparison needs the previous
  version's WIT and `deps/`. When the baseline is the `wire.lock` of a version
  directory, compare with that directory. For a baseline file on its own (a copy
  taken from another revision) the comparison cannot run: say so in the output
  and in the specification; the generators still refuse the root.
- Every difference the generators refuse, not only an alias target: a changed
  dependency version, an added or removed interface, type, or function, a changed
  order, changed stability metadata, and changed docs
  (`dependencies.md`, "Cross-version invariant"). The message is the generators',
  from one shared function.
- `dependencies.md` says that `check` "cannot prove cross-version dependency
  identity" and that CI must also run a generator. That paragraph changes with this
  task.
- A new major: under `W10-093` the pinned-graph rule holds within a major only, so
  `check --first` in `v1.0` does not compare with `v0.x`.
- No released lockfile of a fixture, an example, or alint's contract changes.

## Acceptance criteria

- [x] the specification and the implementation agree on what a canonical type string holds
      for a foreign alias and for a named list, option, or result
- [x] a change of a dependency alias's target, and every other dependency difference the
      generators refuse, fails `check --against` with the message the generators give
- [x] `dependencies.md` states the pinned-graph rule and how a dependency is updated
- [x] no released lockfile in the fixtures or examples changes
