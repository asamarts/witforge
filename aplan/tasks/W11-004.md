## Why

Candidate reviews and maintainer outreach need one evidence standard. Without it, the project can confuse architectural resemblance with an objective consumer benefit, send generic pitches, or count a same-maintainer demonstration as independent adoption.

## Acceptance criteria

- [x] define the evidence required to claim a current use case, duplicated contract source, compatibility problem, or adoption blocker
- [x] separate problems witforge solves now from upstream contract redesigns, missing witforge features, and runtime concerns outside witforge
- [x] define a common fit matrix covering contract shape, execution paths, wire/schema needs, evolution pressure, migration cost, and smallest useful adoption slice
- [x] record the canonical communication channel and contribution policy for every named candidate
- [x] require project-specific, concise, human-authored outreach that links primary evidence and asks falsifiable questions
- [x] define how a maintainer rejection, no demonstrated benefit, or 30-day no-response outcome is recorded without weakening W10-001
- [x] state that examples, forks, and same-maintainer projects do not satisfy independent adoption

## Why it is untestable

This task defines a research and communication protocol. Reverting it cannot make compiled behavior fail.
