## Why

Audit finding A9 (medium, re-run 2026-11-18). `lockfile.md` says `check` "reports every
discrepancy". Reconciliation returns at the first released kind or type change
(`lock.rs:531-538`, `main.rs:480-489`): a v0.2 that retypes four fields, removes one, and adds
two prints one line, so the author fixes the contract one error per run.

```wit
// v0.1: record r { a: string, b: string, c: string, d: string, n1: u8, n2: u8 }
// v0.2: a, b, c, d retyped to u32; n1 removed; two fields added
```

## Edge cases

- The order of the report is the lockfile's key order, the order the rendered file
  uses, and `lockfile.md` says so. Two runs and two machines print one list.
- An entry whose kind and type both changed is one diagnostic naming both.
- A parent that mixes kinds (`W10-045`) is one diagnostic for the parent, not one
  per member.
- Discrepancies of different classes in one run: a kind change, a type change, a
  reintroduction, a reorder (`W10-049`), and a file that is not in canonical form.
  Each is reported, and none hides another.
- With `--against`, discrepancies against the baseline and against the current
  lockfile are both listed.
- Subset violations still end the run before the lockfile is compared
  (`lockfile.md` section 8). That rule does not change.
- `lock` writes nothing when it reports any discrepancy, however many of the
  others it could have reconciled.
- A contract with several hundred discrepancies: every one is printed, or a
  documented cap says how many were left out.
- In JSON and SARIF a discrepancy has the code and path it has when it is the only
  one (`W10-079`).

## Acceptance criteria

- [ ] `check` and `lock` collect every kind change, type change, and reintroduction before
      failing, in a deterministic order
- [ ] the JSON and SARIF reports carry one diagnostic per discrepancy
- [ ] a test asserts the full list for the contract above
