## Why

`rust.rs`, `convert.rs`, and `glue.rs` hardcode `::std::string::String`, `::std::vec::Vec`, and `::std::error::Error`, preventing `#![no_std]` Wasm guest and embedded Rust crates from including generated code directly even though `core::error::Error` is stable since Rust 1.81 (well below MSRV 1.88).

## Decision

- Add opt-in `no_std` mode (`RustOptions`, `rust::plan_with_options`, `GlueOptions`, `glue::plan_with_options`, CLI `--no-std` / `--std` on `rust`, `glue`, `generate`, and `no-std = true` under `[project.<name>.rust]` and `[project.<name>.glue]` in `witforge.toml`).
- Default output (`no_std = false`) remains byte-for-byte unchanged.
- When `no_std = true`, emit `::alloc::string::String`, `::alloc::vec::Vec`, `::core::option::Option`, `::core::result::Result`, `::core::fmt`, and `::core::error::Error`.

## Acceptance criteria

- [ ] Default (`no_std = false`) output is byte-for-byte unchanged
- [ ] `no_std = true` generated plain Rust, `convert.rs`, `worlds.rs`, `witforge_deps.rs`, and glue compile and pass `clippy -D warnings`, `rustfmt --check`, and `-D missing_docs` inside a `#![no_std]` crate with `extern crate alloc;`
- [ ] CLI flags, `witforge.toml` keys, and `docs/guide/reference.md` are tested and documented
