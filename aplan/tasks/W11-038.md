## Why

Audit finding D7 (idea, not a defect). `convert.rs` converts values between versions. A host
that supports several contract versions also needs to call an implementation of the `v0.1`
trait through the `v0.2` trait (and the reverse); today each consumer writes that adapter by
hand from the value conversions.

## Decision

Default chosen while documenting the task on 2026-11-19, not an owner decision.

The task is an evaluation, and its result is one of two. The adapters are
generated when a consumer's hand-written adapter exists and the generated one
would replace it without a change in behaviour. Otherwise the task records a
decline in `docs/design/emitters.md`, with what a consumer would have to show
for it to reopen.

## Edge cases

- Nothing can be measured until a consumer has two versions of one contract. If
  none has, the task records that and waits.
- Both directions: calling a `v0.1` implementation through the `v0.2` trait
  converts parameters new-to-old and the result old-to-new, and the reverse.
- A conversion can fail, and a trait method that does not return a `result` has
  nowhere to report it. What the adapter does then decides the shape of the
  feature.
- A function that exists in only one version, and one whose signature changed.
- Across a major boundary some conversions are omitted (`W10-093`), and with them
  the functions that need them.
- Conversions take references and traits take owned values.
- A decline records what a consumer would have to show for the task to reopen.

## Acceptance criteria

- [ ] measure the hand-written adapter in one real consumer
- [ ] specify adapter generation for functions whose parameters and results convert, and the
      behaviour for functions that exist in only one version
- [ ] the result follows the rule under Decision: the adapters are generated behind an
      option, with a compile test, or the decline and its revisit trigger are recorded
