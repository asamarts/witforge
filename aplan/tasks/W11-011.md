## Why

Conduit ships protobuf/gRPC plugins and core-Wasm processors, while its Component Model direction is under active reconsideration: the current ADR of record adopted it, but a pending ADR proposes making gRPC primary and deferring Component Model connectors. This is a useful multi-transport hypothesis only if the investigation confirms a maintained dual-contract problem.

## Acceptance criteria

- [ ] pin the reviewed ADR chain and ratification status, roadmap, current protobuf protocols, Go plugin interfaces, core-Wasm processor implementation, and Rust SDK plans
- [ ] determine which direction is binding, which contracts are implemented or expected to remain dual-transport, and whether the WIT RFC still represents maintained intent
- [ ] identify exact duplicated source-of-truth, compatibility, or SDK-generation problems that witforge could solve
- [ ] classify streaming, acknowledgements, state/checkpoints, maps, services, resources, and bounded processor operations against witforge 0.4
- [ ] evaluate message/control sub-contracts separately from full connector streams
- [ ] account for the Go-first host and whether Rust/plain-Rust generation is actually valuable
- [ ] record smallest adoption slice, project-side and witforge-side gaps, and go/no-go recommendation
- [ ] apply the external-adoption protocol: label material claims, decide all four gates, complete the six-dimension matrix, state the falsifier, and choose contact, defer, or no-contact
- [ ] record the canonical outreach path: a GitHub Discussion as directed by Conduit's contribution guide

## Why it is untestable

This is an external architecture and adoption-fit review.
