## Why

`main` after 0.6.0 contains the remaining second-audit work. `W10-095` deliberately breaks the
pre-1.0 Rust library API so model, lockfile, and diagnostic types can evolve compatibly after
1.0; `W10-096` replaces stringly library findings and moves compiler orchestration out of the
CLI; `W10-094` carries WIT stability and deprecation metadata into generated output. These
changes must ship together in a pre-1.0 minor with one migration section before the 1.0 API is
frozen. No existing task owns that release.

## Why it is untestable

Publication is proved by the exact-commit `ci ok` result, the release workflow, install checks,
and the published artifacts rather than by a repository test that could fail if this task were
reverted.

## Decision

The release is 0.7.0. It is the single planned pre-1.0 exception to minor-version Rust library
API compatibility. The exception permits only the checked cargo-semver failures and complete
W10-094/W10-095/W10-096 rustdoc API delta before and on the 0.7.0 tag commit; once that tag is
an ancestor, the ordinary minor gate returns automatically for every later pre-1.0 and 1.x release.

## Edge cases

- The release-preparation commit moves workspace, CLI dependency, changelog, README, and docs
  versions while CI's published Action remains on 0.6.0 until the 0.7.0 tag and assets exist.
- The changelog separately identifies Rust library source breaks, generated-output changes,
  and newly rejected inputs, with a concrete migration for each affected consumer.
- The release workflow must accept exactly the reviewed 0.7.0 API break without weakening the
  protobuf-history, generated-output, MSRV, security, package, or Action gates.
- The post-release commit moves CI's published Action pin to 0.7.0 and leaves the semver gate
  active for the next release.
- alint regenerates with the released binary and passes before this task closes.
