## Why

Audit finding A5 (high). The `# witforge order v1` section is what makes a reorder of a
released record's fields or a function's parameters a detected source-breaking change. The
reader accepts a lockfile whose order lines are missing, and `check --first` skips the
comparison (`lock.rs:478-485`, `565-567`, `295-301`, `627`; `main.rs:495-515`).

## Reproduction (re-run 2026-11-18)

```wit
// wit/v0.1/c.wit (released)
package ex:t@0.1.0;
interface api {
  record r { a: u32, b: string }
  get: func(x: u32, y: string) -> r;
}
// wit/v0.2/c.wit: fields and parameters reversed
//   record r { b: string, a: u32 }
//   get: func(y: string, x: u32) -> r;
```

Copy `wit/v0.1/wire.lock` to `wit/v0.2/`, delete the `# order ex:t/api/r …` and
`# order ex:t/api#get …` lines, and run the default `witforge check wit/v0.2`,
`witforge rust wit`, and `witforge proto wit`: all exit 0, and the generated trait is
`fn get(&self, y: String, x: u32)`. Only `check --against` (exit 1) and a direct `diff`
(`reordered`) notice.

Also re-run: `check --first` passes with a stale order section that the default `check`
rejects. Reviewer-run: an order line rewritten to a subset of the members, to names that are
not members, or for a parent that does not exist is accepted when its fingerprint is valid.

## Acceptance criteria

- [ ] a lockfile must carry exactly one order line for every parent that has ordered members,
      naming exactly that parent's live members; a missing, extra, or wrong line is exit 1
- [ ] `check` runs that validation in the default, `--first`, and `--against` modes
- [ ] the generators refuse a lockfile that fails it
- [ ] tests cover a deleted line, a subset, a non-member, and an unknown parent
