## Why

`ReleasedManifest` rejects a symlinked version directory but accepts a symlinked
`wire.lock`; a released directory with a symlinked lockfile passed `witforge check` in a
probe. `ci/check-release-freeze.sh` catches tracked symlinks in CI, but a standalone
`check` does not enforce the released-directory boundary it claims to verify.

## Acceptance criteria

- [x] a released version directory is refused when `contract.wit`, `wire.lock`, or a
      `deps/` tree contains a symlink that the tool would read
- [x] the same check is reachable from `check` and the released-manifest loader, with exit
      codes consistent with existing contract/released violations
- [x] non-released version-directory behavior and atomic-lock replacement are unchanged
- [x] CLI regressions cover the released symlinked-lockfile case
- [x] `docs/design/lockfile.md` states the tool-level boundary and what remains exclusive to
      the history-based freeze script

## Verification

- `check_refuses_a_symlink_inside_a_released_directory` covers a symlinked `wire.lock` and a
  recursive symlinked `deps/` entry.
- `cargo test --workspace --locked`, MSRV 1.88, Clippy, rustdoc, generated output, release
  freeze, security, and aplan gates pass.
