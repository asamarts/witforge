## Why

Audit finding D2 (medium, re-run in the first audit pass). `@deprecated`, `@since`, and
`@unstable` are accepted and produce nothing in any output. `model::Stability` has no
deprecated state (`model.md:283` defers it). In an append-only contract, deprecation is the
only way to retire a member, so the one signal an author has does not reach consumers.

Adding a variant to `Stability` after 1.0 would be a breaking library change unless
`W10-095` lands first.

## Decision

Defaults chosen while documenting the task on 2026-11-19, not owner decisions.

- `@unstable` stays metadata. `lockfile.md` section 7 already says that every item
  in a version directory is part of that version, unstable ones included. The
  item is generated as now, and its doc comment says that it is unstable and
  names the feature. Refusing it would reject contracts that are accepted today,
  and a cargo feature would make generated code depend on the consumer's feature
  set.
- `@since` is checked where it can be: against the version directory that first
  declares the item, when the root holds that directory. A check of a single
  directory cannot know and does not check.
- `wit-parser` 0.263 accepts `@deprecated(version = x.y.z)` only beside
  `@since` or `@unstable`; it has no source `note` operand. The model records a
  deterministic generated note naming the WIT deprecation version so Rust's
  `#[deprecated]` has actionable text.
- Annotation versions must be `<major>.<minor>.0`, cannot be later than the
  containing package version, and a deprecation version cannot predate its
  `@since` version.
- Root validation checks a `@since` value only when that exact version is
  present: it must be the first root version declaring the annotated item. A
  root that does not contain the claimed version cannot prove when the item was
  introduced and does not reject it.
- Dependency stability and docs remain part of the exact pinned graph.
  Deprecating a dependency item within one root major is therefore refused.
- Worlds and world imports/exports have no standalone plain-Rust, protobuf, or
  JSON Schema declaration to annotate. Their metadata remains in the model,
  appears in Rust world-metadata documentation, and participates in `diff`;
  this task does not invent a second generated world representation.

## Edge cases

- Where WIT allows the annotations: on interfaces, types, functions, and world
  items. If a field or a case cannot carry one, say that a single member cannot
  be deprecated.
- What the parser requires: whether `@deprecated` needs `@since` or `@unstable`
  beside it. Test it and follow it.
- Generated code uses the deprecated items itself: glue, `convert.rs`, and the
  trait. It allows the lint where it does, so a consumer's `-D warnings` build
  passes and the consumer's own uses still warn.
- prost turns `deprecated = true` into its own attribute on the generated type.
  Check what a consumer's build then reports.
- `"deprecated": true` is not a Draft 7 keyword. A Draft 7 validator ignores it;
  the validator the tests use must not reject it.
- `diff`: a newly deprecated item is a change that breaks none of the three
  views. Removing a deprecation is reported the same way.
- Stability is not wire identity, and the lockfile does not change.
- The pinned dependency graph includes stability metadata (`dependencies.md`), so
  deprecating a dependency's item between two versions of one major is refused
  by that rule today. Decide whether that stays.
- A version in an annotation that is not `<major>.<minor>.0`, or that is later
  than the directory it is in.
- `model::Stability` gets a new state, which is why `W10-095` comes first.

## Acceptance criteria

- [x] the model records deprecation with its version and note
- [x] plain Rust emits `#[deprecated]`, protobuf emits `deprecated = true`, JSON Schema
      emits `"deprecated": true`
- [x] `diff` reports a newly deprecated member as a non-breaking change
- [x] `@unstable` is specified as metadata: the item is generated, and its doc comment says
      that it is unstable
- [x] `@since` is checked against the version directory that first declares the item when
      the root holds it, and the specification says when it cannot be checked
