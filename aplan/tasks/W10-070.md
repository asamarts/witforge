## Why

Audit finding B13 (high, re-run in the first audit pass). The JSON Schema for a result with a
payload-less side cannot express that side (`json_schema.rs:266-281`):

```text
result<_, E>   accepts only {"err": …}      Ok(()) has no valid document
result<T>      accepts only {"ok": …}       Err(()) has no valid document
result         is {} with maxProperties 0   ok and err are indistinguishable
```

`emitters.md` section 10.2 specifies exactly this shape, so the defect is in the
specification. Reviewer-run lows: `f32` has no bounds, `integer` accepts `1.0`, and 64-bit
bounds exceed what a JSON number holds exactly (2^53).

## Decision recorded here

Recommendation: a payload-less side is `{"ok": null}` or `{"err": null}`, so every result is
an object with exactly one of two keys. This changes the 0.5.0 schema output for the three
shapes above, which were unusable. Decide at the same time whether 64-bit integers are JSON
numbers or strings (protobuf JSON uses strings) and whether this schema is meant to describe
the `--serde` output (`W10-071`).

## Acceptance criteria

- [ ] every value of every supported result type has exactly one valid document, proved by a
      test that validates generated instances against the schema
- [ ] the 64-bit and `f32` representation is specified and tested
- [ ] `conformance.md` gains the JSON Schema mapping row
