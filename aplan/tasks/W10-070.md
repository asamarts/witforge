## Why

Audit finding B13 (high, re-run in the first audit pass). The JSON Schema for a result with a
payload-less side cannot express that side (`json_schema.rs:266-281`):

```text
result<_, E>   accepts only {"err": …}      Ok(()) has no valid document
result<T>      accepts only {"ok": …}       Err(()) has no valid document
result         is {} with maxProperties 0   ok and err are indistinguishable
```

`emitters.md` section 10.2 specifies exactly this shape, so the defect is in the
specification. Reviewer-run lows: `f32` has no bounds, `integer` accepts `1.0`, and 64-bit
bounds exceed what a JSON number holds exactly (2^53).

## Decision

Decided by the owner on 2026-11-19: every result is a JSON object with exactly one
key, `ok` or `err`. A side without a payload has the value `null`, which is how a
variant case without a payload is already written. This changes the 0.5.0 schema
of `result<_, E>`, `result<T>`, and bare `result`, none of which could express
every value. The task ships in 0.6.0 (`W10-069`).

Defaults chosen while documenting the task on 2026-11-19, not owner decisions:

- 64-bit integers stay JSON numbers, with their exact bounds in the schema and a
  stated caveat: a reader that parses numbers as IEEE 754 doubles is exact only up
  to 2^53. Writing them as strings belongs to the opt-in aligned-JSON profile
  (`W11-035`).
- The schema keeps describing the WIT names, not the `--serde` output. Aligning the
  two is `W11-035`, and `W10-071` documents how they differ.

## Edge cases

- The four result forms: `result<T, E>`, `result<T>`, `result<_, E>`, and bare
  `result`. Each as a named type, a field, a list element, an option payload, a
  variant payload, and a side of another result.
- A payload that itself accepts `null`: in `result<option<T>, E>`, `{"ok": null}`
  is `Ok(None)`, and it is unambiguous because the key carries the side.
- Documents that must be rejected: `{}`, `{"ok": 1, "err": 2}`, an unknown key, and
  `null`.
- `option<option<T>>` is `anyOf` inside `anyOf`: `None` and `Some(None)` are both
  `null`. The criterion "exactly one valid document per value" is about results.
  State the nested-option limit in section 10.2; `W10-071` states the same limit
  for Serde.
- Floats: `f32` and `f64` are `number`; NaN and the infinities have no JSON form.
  Decide whether `f32` gets its finite bounds, and say that the schema accepts
  values that `f32` cannot hold exactly.
- Draft 7 `integer` accepts `1.0`. That is the vocabulary's definition, not an
  emitter defect; document it.
- The golden schema of every fixture with a payload-less result side changes. The
  migration section says how to find such a type.
- `docs/guide/json-projections.md` and section 10.2 show the new shape beside the
  Serde shape (`{"Ok": …}`).
- `conformance.md` got its JSON Schema row on 2026-11-18 (`W10-043`). What remains
  is that the row's fixture contains the four result forms.

## Acceptance criteria

- [ ] every value of every supported result type has exactly one valid document, proved by a
      test that validates generated instances against the schema
- [ ] the 64-bit and `f32` representation is specified and tested
- [ ] the fixture behind the JSON Schema row of `conformance.md` holds the four result
      forms, and the migration section of the changelog describes the changed shapes
