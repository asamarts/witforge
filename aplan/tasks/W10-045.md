## Why

Audit findings A1 (critical) and A7 (medium). A released named type can change kind without
any gate noticing, as long as the new members have new names. The lockfile then keeps the old
members as reserved entries of one kind next to live entries of another kind under the same
parent, and every field that refers to the type silently changes its wire shape.

## Reproduction (re-run 2026-11-18)

```wit
// wit/v0.1/c.wit, locked with --first and listed in wit/released
package ex:k@0.1.0;
interface types {
  enum color { red, green }
  record r { c: color }
}
// wit/v0.2/c.wit: the same, except
//   record color { hue: u32 }
```

`witforge lock wit/v0.2 --against wit/v0.1/wire.lock`, `check --against`, `proto`, `glue`,
and `schema` all exit 0. `diff` prints `kind-changed … wire:compatible`. In `v0.proto`,
`r.c = 1` changes from `optional TypesColor` (an enum) to a message, and `message TypesColor`
carries no `reserved 1, 2` for the old cases. Only `witforge rust` refuses, through the
conversion generator. The reviewer ran all twelve ordered pairs among enum, flags, record,
and variant with the same result.

Code: `model.rs:427-435`, `lock.rs:514-562`, `diff.rs:707-726`, `proto.rs:627`.

## Approach

Refuse a parent whose live and reserved members do not all have one kind. This needs no
lockfile format change. A transition between two memberless shapes is already caught because
the canonical type of every referring member changes.

## Edge cases

- All twelve ordered pairs among enum, flags, record, and variant, with disjoint
  member names. A pair that shares a member name is already refused as a kind
  change of that entry and stays covered.
- A type whose released members are all reserved, with live members of another
  kind. This is also what removing a type in one version and adding a type of
  another kind under the same name in a later version produces. Refused; the
  remedy is a new name.
- A type that changes kind inside one unreleased draft is not refused: its draft
  entries are dropped and leave no reservation (`lockfile.md` section 6).
- Method and parameter parents hold one kind by construction. The reader's check
  that an entry's kind fits its key shape is `W10-053`.
- A payload added to or removed from a variant case is a type change of one kind,
  not a mix, and is already refused.
- A released directory that already mixes kinds, locked by 0.5.0 or earlier. The
  directory is frozen, so the refusal makes the whole root ungeneratable. Default:
  refuse anyway and say so in the migration section, because the schema of such a
  contract has already changed shape and no known contract is in that state.
  Check every fixture, both examples, and alint's contract before the release.
- `diff` must still be able to report the change. A direct endpoint whose new side
  mixes kinds is reported as a wire-breaking kind change (exit 1 under `--check`),
  not as a load failure with exit 2.
- The refusal is in the shared loader, so `rust`, `proto`, `schema`, and `glue`
  give the message `check` gives. A per-emitter check would let them drift again.
- Reserved numbers and names of a type, and the method ids of an interface that no
  longer exists, appear as `reserved` in the proto output, in the major's shared
  file, however many minors ago the member was removed.

## Acceptance criteria

- [x] reconciliation refuses, with exit 1 and a message naming the parent and both kinds, any
      contract that would give one parent members of two kinds
- [x] `check` refuses a lockfile that already holds a mixed-kind parent
- [x] a test covers all twelve ordered kind pairs for `lock --against`, `check --against`,
      `proto`, `glue`, and `schema`
- [x] `diff` classifies a kind change as wire-breaking and `diff.md` says so
- [x] proto output reserves every reserved number and name, including the method ids of an
      interface that no longer exists (reviewer-run: those are dropped today)
- [x] the changelog tells an owner of an unreleased draft that already mixes kinds how to
      recover (rename the type)
