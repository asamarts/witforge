## Why

While each `W13-002..W13-011` task already wires its own language config table into `witforge.toml` and `witforge generate`, users also need selective generator filtering (`witforge generate --only <list>`), an explicit security opt-in (`--allow-plugins`, off by default) before `witforge generate` ever executes configured `W11-001` plugins, matching GitHub Action `generators:` support, and a consolidated polyglot CI matrix.

## Decision

- `witforge generate` must **never** execute configured `[project.<name>.plugins.*]` entries unless `--allow-plugins` is explicitly passed on the CLI (preventing untrusted `witforge.toml` files from running binaries implicitly).
- Add `--only <GEN[,GEN...]>` to `witforge generate` with strict `WF9001` validation against known built-in generator names (`rust`, `proto`, `schema`, `glue`, `doc`, `ts`, `ts-glue`, `py`, `py-glue`, `go`, `go-glue`, `java`, `java-glue`, `csharp`, `csharp-glue`, `plugins`).

## Acceptance criteria

- [ ] Add `--only` and opt-in `--allow-plugins` (default false) to `witforge generate`, proving configured plugins are skipped/refused unless `--allow-plugins` is supplied and existing projects without polyglot/plugin config remain unchanged
- [ ] Extend `action.yml`, `action/index.js`, and `action/test.js` (`generators:` allowlist) to support polyglot built-in emitters while keeping plugin execution opt-in
- [ ] Consolidate and verify the SHA-pinned multi-language CI conformance matrix in `.github/workflows/ci.yml` across Rust, TypeScript, Python, Go, Java 21, and .NET 8
