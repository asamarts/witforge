# Non-Rust implementations

witforge emits protobuf schema for cross-language values and calls. Use the normal protobuf
generator for the target language, such as `protoc-gen-go`, `ts-proto`, `grpcio-tools`, or the
standard Java, Kotlin, C#, C++, or Swift generator. witforge does not generate language SDKs,
services, or transport framing.

## Protobuf file options

By default, emitted `.proto` files carry no language-specific file options so output remains
neutral across every target language. If you want generated `.proto` files to embed idiomatic
Go, Java, or C# placement options directly, opt in via `[project.<name>.proto]` in `witforge.toml`
or the matching flags on `witforge proto`:

```toml
[project.example.proto]
out = "generated/proto"
go-package = "github.com/acme/contracts/gen/go"
java-package = "com.acme.contracts"
java-multiple-files = true
csharp-namespace = "Acme.Contracts"

# Optional exact overrides keyed by emitted proto package name (including
# disambiguated dependency packages such as `shared.types.v0_m1`):
[project.example.proto.packages."example.plugin.v0"]
java-outer-classname = "PluginV0Proto"
```

Or on the command line:

```sh
witforge proto wit --out generated/proto \
  --go-package github.com/acme/contracts/gen/go \
  --java-package com.acme.contracts \
  --java-multiple-files \
  --csharp-namespace Acme.Contracts
```

How each option is derived across multiple majors (`v0`, `v1`) and `deps/` dependency files:

- `go-package`: a base import path prefix without `;` derives
  `<prefix>/<ns>/<name>/<ver>;<ns>_<name>_<ver>` for every emitted file (for example
  `github.com/acme/contracts/gen/go/example/plugin/v0;example_plugin_v0`). An explicit
  `<import/path>;<alias>` value (which must include `/`) is accepted verbatim when at most one
  emitted file inherits it and refused when multiple emitted files would share it.
- `java-package`: derives `<prefix>.<proto_package>`, escaping Java reserved keywords with a
  trailing underscore (for example `default` becomes `default_`). Two emitted files in the same
  effective Java package cannot emit colliding top-level Java class names (including `Empty.java`
  under `java-multiple-files = true` or implicit default outer classnames).
- `java-multiple-files`: emits `option java_multiple_files = true;` (or `false;` in config).
  Pass `--no-java-multiple-files` on the CLI to omit the option when overriding config.
- `java-outer-classname`: validated as a Java type identifier (rejecting keywords and restricted
  type identifiers such as `record` and `var`) and refused if it collides with any generated
  message, enum, wrapper, `<Message>OrBuilder`, enclosed `Builder`/`*Case` class, or another
  emitted file's Java class in the same effective Java package.
- `csharp-namespace`: derives `<prefix>.<PascalCaseSegments>` (for example `example.my_pkg.v0`
  becomes `Acme.Contracts.Example.MyPkg.V0`, and a disambiguated dependency `shared.types.v0_m1`
  becomes `Acme.Contracts.Shared.Types.V0M1`). Two emitted files resolving to the same C#
  namespace are refused because every generated `.proto` file defines `message Empty`.

File options are strictly non-wire metadata: they never alter `wire.lock`, protobuf binary wire
encoding, `witforge diff --check=wire,decode`, Rust module paths generated by `witforge-build` /
`prost-build`, or `witforge glue`.

If you prefer to keep zero language options in checked-in `.proto` files, both `protoc`
(`--go_opt=Mv0.proto=github.com/acme/contracts/gen/go/v0`) and `buf` managed mode
(`buf.gen.yaml` `managed.override`) can inject Go, Java, and C# placement outside the schema.
Note that `buf breaking` with its default `FILE` rules flags changed file options once if you
enable file options on an already-published contract; either opt in before your first release or
temporarily exclude `FILE_SAME_*` option checks for that transition commit.

## Decode profile

The generated protobuf type alone is not the complete WIT value contract. Some WIT rules cannot
be expressed by proto3 syntax and are enforced by witforge's generated Rust glue. A non-Rust host
or a protocol with two non-Rust endpoints must enforce the same rules explicitly.

| WIT value | Protobuf projection | Required implementation behavior |
|---|---|---|
| `u8`, `u16` | `uint32` | Reject values above the WIT type's maximum. |
| `s8`, `s16` | `sint32` | Reject values outside the WIT type's signed range. |
| `char` | `uint32` | Reject code points that are not valid Unicode scalar values (surrogates `0xD800..=0xDFFF` and values `> 0x10FFFF`). |
| required scalar, string, enum, `list<u8>`, or `list<u8, N>` | proto3 `optional` scalar/string/enum/bytes | Reject absence. A scalar's protobuf default is not a substitute for presence. |
| `option<T>` | the same optional or wrapper shape used for `T` | Permit absence as `None`; validate a present payload normally. |
| required record, variant, flags, result, parameter, or message result | message field | Reject absence. |
| `list<T>` | `repeated T`, or a wrapper when nested | Empty is valid. Validate every element recursively. |
| `list<T, N>` | `optional bytes` (when `T` is `u8`) or `repeated singular(T)` (or list wrapper when nested) | Require exact length `N` (`1 <= N <= 65536`), rejecting shorter or longer payloads (`InvalidLength`). Validate every element recursively. |
| `map<K, V>` | `map<K', singular(V)>`, or a `WitforgeMapOf...` wrapper when nested | Empty is valid. Validate narrow integer keys (`u8`/`u16`/`s8`/`s16`), `char` keys, and every value recursively. |
| enum | protobuf enum with `UNSPECIFIED = 0` | Reject zero and unknown numeric values; WIT enums are closed. |
| variant or result | message with a `oneof` | Require one known case. Reject an unset or unknown case. |
| flags | message with one `bool` per flag | Treat missing/default `false` as an unset flag. |
| nested option/list/result wrapper | synthesized message | Require the wrapper's `oneof` (`none`/`some` or `ok`/`err`) to be set; reject an unset or unknown wrapper state. |

These rules apply to record fields, function parameters, and function results. They also apply
after protobuf binary or proto3-JSON parsing. Language protobuf libraries commonly preserve an
unknown enum number or expose a `uint32` without the narrower WIT range; successful protobuf
parsing therefore does not establish a valid WIT value.

A Rust endpoint using generated glue returns `GlueError` for these cases. Other implementations
should expose errors appropriate to their application while preserving the same accept/reject
boundary.

## Conformance fixture bundle

Use `witforge conformance` to export witforge's built-in, deterministic cross-language conformance
bundle (`conformance_version = 1`) and verify your non-Rust protobuf glue against the exact same
decode and encode rules proved against witforge's Rust glue:

```sh
witforge conformance --out conformance-bundle --polyglot-proto-options
witforge conformance --out conformance-bundle --polyglot-proto-options --check
```

The command writes two directories and a top-level manifest under `--out`:

- `wit/v0.1/`: the canonical WIT conformance contract (`contract.wit`, `deps/conformance-dep/dep.wit`,
  and `wire.lock`) exercising all 13 decode-profile rows, foreign `deps/` types, and interface
  functions.
- `proto/`: the emitted `.proto` files (`v0.proto` and `witforge.conformance_dep.v0.proto`). Files
  are neutral by default; pass `--polyglot-proto-options` (or explicit `--go-package`,
  `--java-package`, `--java-multiple-files`, `--java-outer-classname`, `--csharp-namespace`) to
  embed Go, Java, and C# placement options.
- `vectors.json`: deterministic test vectors carrying RFC 4648 base64 binary protobuf payloads,
  canonical proto3-JSON payloads, expected `accept`/`reject` outcomes, canonical error kinds
  (`IntegerOutOfRange`, `MissingField`, `UnknownEnumValue`, `UnknownCase`, `InvalidState`,
  `InvalidChar`, `InvalidLength`), and `encode`-direction boundary rejection vectors for languages
  without native narrow/unsigned/scalar-char/fixed-array types.

The built-in vectors cover:

- every narrow integer's minimum, maximum, and out-of-range values plus 64-bit integers beyond
  `2^53 - 1` (`u64::MAX`, `i64::MIN`, `i64::MAX`, `9007199254740993`, `-9007199254740993`);
- `char` boundary scalars (`U+0000`, `U+D7FF`, `U+E000`, `U+1F680`, `U+10FFFF`), multi-byte UTF-8
  strings with embedded NUL, UTF-16 surrogates (`0xD800..=0xDFFF`), and values above `0x10FFFF`;
- `f32`/`f64` finite boundaries, `-0.0`, `NaN`, `Infinity`, and `-Infinity`;
- required optional/message fields present (including explicit zero/empty defaults) and absent;
- `option<T>` absent and present, including `option<option<T>>`, `option<list<T>>`, and
  `option<map<K, V>>`;
- closed enums (`0`, known cases, and unknown numbers) in both root and `deps/` packages;
- every variant case, all four `result` forms (`result<T, E>`, `result<T>`, `result<_, E>`,
  `result`), unset variant/result oneofs (`UnknownCase`), and unset `WitforgeOptionOf*` wrappers
  (`InvalidState`);
- empty and populated lists, fixed-length `list<u8, N>` and `list<T, N>` with exact length `N`,
  `N - 1`, and `N + 1`, and nested list/option/result wrappers;
- `map<K, V>` across string, narrow integer, `char`, `bool`, and 64-bit keys plus nested maps;
- interface function request and response wrappers (including foreign `deps/` parameters and
  no-result functions), in both protobuf binary and proto3-JSON forms;
- encode-side (`toProto`) boundary rejection vectors for TypeScript, Python, Go, Java, and C#.

Run the vectors through your target language's protobuf implementation and keep `--check` in CI to
detect drift. Generated-file `--check` proves schema reproducibility; running `vectors.json` proves
runtime wire-contract parity with Rust glue.

## JSON is a separate choice

Proto3-JSON follows protobuf naming and presence rules. It is not the JSON shape described by
witforge's JSON Schema (Draft 7 default, opt-in Draft 2020-12) and it is not necessarily the shape
produced by Serde on generated plain Rust types. See [JSON projections](json-projections.md) before
choosing a JSON boundary.

Protovalidate annotations are not emitted today; they would expand the generated `.proto` schema
and consumer runtime/tooling requirements and remain deferred behind an explicit future option if
an adopter demonstrates a need beyond checked glue and conformance fixtures.
