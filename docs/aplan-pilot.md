# aplan pilot: witforge

Started 2026-10-27. This is the dogfooding log for using `aplan` as witforge's
task-level source of truth. Record friction here before working around it; report
the upstream issue when it is reproducible and relevant beyond this repository.

## Scope

- Plan: `aplan/tasks/` with `M-p0` … `M-p6` cuts.
- Policy: `.aplan.yml` (`deny_warnings: true`, test-strength evidence,
  `untestable` exemption, one cut per task).
- Agent contract: `AGENTS.md`, generated by `aplan export-agents-md --write`.
- Tool under test: `aplan 0.5.0-dev` at `~/.local/bin/aplan`;
  source checkout at `~/projects/aplan`.

## Observations

- `aplan init` produces a useful, fully documented starter policy. Setting
  `root: aplan/tasks` makes `add` write files where the plan README describes
  them; the default root is the plan directory itself.
- `aplan add --from` accepts a JSON list as YAML. This made it practical to
  generate a 43-task, seven-cut plan from one reviewed data structure rather
  than hand-editing frontmatter.
- Creating a cut with its work in one batch works as documented: `cut: M-pN`
  joins the task to the milestone, and the milestone holds the members.
- Trace anchors are strict GitHub slugs. `## 5. Output, \`--check\`, and CLI`
  resolves as `5-output---check-and-cli`; the dash count is easy to get wrong.
  `add --from` refused the whole batch with the exact bad anchor, which is the
  right failure mode.
- The initial plan validates: `aplan check` reports 43 tasks, 0 warnings, an
  acyclic DAG; `aplan verify` resolves evidence (none closed yet);
  `aplan export-agents-md --check` passes; `aplan check-docs` sees 10 documents
  and no dangling task reference.
- `aplan summary` reports 105 effort days across the six delivery cuts plus the
  adoption cut, and `aplan roadmap` renders the cut rollups and critical path.
- The `add --from` body is the right hook for authored `## Why` and
  `## Acceptance criteria` sections; the scaffold prompt is avoided entirely.
- `deny_warnings` plus `require_effort` and `require_cut_membership` make the
  first plan honest, but also make an incomplete batch fail loudly. That is the
  desired direction.
- `aplan verify` needs configured runners even before any task is `done`; the
  two cargo runners let future code tasks cite real test names.

## Open questions / friction

1. **CI availability.** The self-hosted witforge runner image does not include
   `aplan`, and the local build is a pre-release (`0.5.0-dev`). A CI gate needs a
   pinned, reproducible binary and a defined update path. Tracked as part of the
   CI/release cut.
2. **Plan/document membership.** `docs.paths` is configured, but the ROADMAP does
   not yet declare cut membership in a `**Tasks:**` line. `aplan check-docs`
   should be evaluated before adding a duplicate task list to the narrative.
3. **Test-name stability.** The evidence policy is test-strength. Renaming a
   test invalidates a closed task's citation; the plan should use module-qualified
   test names and repair citations with `aplan amend` rather than weakening the
   policy.
4. **Generated agent block.** `aplan export-agents-md --write` writes a second
   copy of the policy by design. Keep the hand-written project instructions
   outside the generated markers, and gate the block with `--check`.
5. **Pre-release surface.** Aplan changes behavior between `0.5.0-dev` builds;
   pin the binary used for a release decision, not just `aplan` on `PATH`.

## Actions

- Keep `aplan check`, `aplan verify`, and `aplan export-agents-md --check` in the
  pre-commit loop.
- Add the CI gate task only when a pinned `aplan` binary is available on the
  runner.
- Re-read this log at each cut boundary and record what changed.
