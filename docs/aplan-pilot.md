# aplan pilot: witforge

Started 2026-10-27. This is the dogfooding log for using `aplan` as witforge's
task-level source of truth. Record friction here before working around it; report
the upstream issue when it is reproducible and relevant beyond this repository.

## Scope

- Plan: `aplan/tasks/` with `M-p0` … `M-p6` cuts.
- Policy: `.aplan.yml` (`deny_warnings: true`, test-strength evidence,
  `untestable` exemption, one cut per task).
- Agent contract: `AGENTS.md`, generated by `aplan export-agents-md --write`.
- Tool under test: `aplan 0.5.0-dev` at `~/.local/bin/aplan`;
  source checkout at `~/projects/aplan`.

## Observations

- `aplan init` produces a useful, fully documented starter policy. Setting
  `root: aplan/tasks` makes `add` write files where the plan README describes
  them; the default root is the plan directory itself.
- `aplan add --from` accepts a JSON list as YAML. This made it practical to
  generate a 44-task (37 work tasks plus 7 milestones), seven-cut plan from one
  reviewed data structure rather than hand-editing frontmatter.
- Creating a cut with its work in one batch works as documented: `cut: M-pN`
  joins the task to the milestone, and the milestone holds the members.
- Trace anchors are strict GitHub slugs. `## 5. Output, \`--check\`, and CLI`
  resolves as `5-output---check-and-cli`; the dash count is easy to get wrong.
  `add --from` refused the whole batch with the exact bad anchor, which is the
  right failure mode.
- The initial plan validates: `aplan check` reports 44 tasks, 0 warnings, an
  acyclic DAG; `aplan verify` resolves evidence (none closed yet);
  `aplan export-agents-md --check` passes; `aplan check-docs` sees 10 documents
  and no dangling task reference.
- `aplan summary` reports 109 effort days across the six delivery cuts plus the
  adoption cut. At 4 productive effort days/week that is 19.3 weeks to 0.1 and
  27.2 weeks to 1.0, inside the roadmap's 13–20 and 26–45 week ranges; the
  earlier 5-day assumption put the full plan below the 1.0 range.
- The `add --from` body is the right hook for authored `## Why` and
  `## Acceptance criteria` sections; the scaffold prompt is avoided entirely.
- `deny_warnings` plus `require_effort` and `require_cut_membership` make the
  first plan honest, but also make an incomplete batch fail loudly. That is the
  desired direction.
- `aplan verify` needs configured runners even before any task is `done`; the
  two cargo runners let future code tasks cite real test names.

## Open questions / friction

1. **CI availability.** The self-hosted witforge runner image does not include
   `aplan`, and the local build is a pre-release (`0.5.0-dev`). A CI gate needs a
   pinned, reproducible binary and a defined update path. Tracked as part of the
   CI/release cut.
2. **Plan/document membership.** `docs.paths` is configured, but the ROADMAP does
   not yet declare cut membership in a `**Tasks:**` line. `aplan check-docs`
   should be evaluated before adding a duplicate task list to the narrative.
3. **Test-name stability.** The evidence policy is test-strength. Renaming a
   test invalidates a closed task's citation; the plan should use module-qualified
   test names and repair citations with `aplan amend` rather than weakening the
   policy.
4. **Generated agent block.** `aplan export-agents-md --write` writes a second
   copy of the policy by design. Keep the hand-written project instructions
   outside the generated markers, and gate the block with `--check`.
5. **Pre-release surface.** Aplan changes behavior between `0.5.0-dev` builds;
   pin the binary used for a release decision, not just `aplan` on `PATH`.

## Adversarial audit of the first plan

The first plan was audited before implementation and corrected:

- Added `W4-007` for the missing proto command/output/`--check` surface.
- Made every post-0.1 task depend on the 0.1 release (`W5-005`), so `ready`
  cannot offer phase-6 work before 0.1 ships.
- Added the missing `W2-006` dependency to the CI gate and the two-version
  documentation task, and the missing `W4-007` dependency to consumer validation.
- Split overlapping test scope: canonical/unit tests stay in the model tasks;
  the comprehensive fixtures and property tests belong to `W2-006`/`W1-004`.
- Moved the released renumbering/type checks from `W2-003` to `W2-004`, where
  the previous-baseline mode exists, and kept `W2-003` on default-mode reconcile.
- Added documentation paths to `W6-001` and `W6-009` so their design/release
  changes are covered by evidence.
- Corrected the pre-emitter CLI acceptance: `W2-005` wires `check`/`lock`, while
  `W3-003`, `W4-007`, and `W4-006` wire their own subcommands.
- Added the missing Cargo path coverage for new dependencies and the missing
  `W5-003`/`W5-004`/world/config dependency edges.
- Raised the CLI and release estimates after reviewing their scope.
- Narrowed `W5-004` to measurement/triage; the individual pre-golive decisions
  belong to `W6-001` through `W6-006`.

## Adversarial evaluation (W5-003)

The alint end-to-end test now also exercises the hostile cases that golden output alone cannot
prove:

- absent required scalars, bytes, and message fields (`repo-resource.path`, `finding.message`,
  `adapter-input.max-rows`, `row.resource`, `adapter-input.bytes`) are `MissingField`;
- optional `repo-resource.index`, `row.pointer`, `row.label`, `finding.path`, and optional
  timestamp fields accept absence without becoming missing;
- required repeated collections accept empty lists;
- unset `Node`, `RowState`, and `AdapterError` oneofs are `UnknownCase`;
- unknown enum values and zero are exercised against the enum-bearing glue contract fixture
  (`conversions_compile_and_run_against_generated_types`);
- the full CLI output is byte-identical across repeated runs and clean under `--check`.

No new contract gap was found. The alint fixture README continues to record the source
adaptations that were already known; this evaluation did not require another design exception.
