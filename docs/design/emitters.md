# witforge emitter conventions (Rust, protobuf, JSON Schema, glue)

Status: specified 2026-10-26; implemented 2026-10-29, with JSON Schema added 2026-11-01.
This document is normative for generated Rust, protobuf, JSON Schema, and glue output. The lockfile format and `check`/`lock` semantics are in
[`lockfile.md`](lockfile.md); the product decisions are logged in
[`overview.md`](overview.md#9-decision-log).

The key words MUST, MUST NOT, SHOULD, and MAY are used as in RFC 2119.

## 1. Common conventions

- Emitters consume the internal model, not `wit-parser` types directly. The model is specified
  in [`model.md`](model.md); its conversion module is the only place that follows upstream
  changes.
- Output is deterministic: LF line endings, a final newline, no timestamps, no tool version, no
  absolute paths, and no dependence on hash-map iteration order. Items are emitted in WIT source
  order; version modules, schema files, and proto files are emitted in ascending semver order.
  Proto reserved
  declarations use ascending numbers and lexicographically sorted names as separate `reserved`
  statements.
- Every generated file starts with a stable ownership header. Rust, proto, and glue use a line
  comment; JSON Schema uses a valid JSON `$comment` prefix:

  ```rust
  // @generated by witforge; do not edit.
  // source: example:plugin@0.1.0
  ```

  `mod.rs` uses the package name without a version; per-version Rust files and per-major proto
  files use the source package version that produced them. JSON Schema uses the first-line
  `$comment` form specified in section 10.1.
- Generated files are owned by witforge. Generation overwrites expected files and deletes stale
  files in the output root that carry the generated header. `--check` reports missing, changed,
  or extra generated files and writes nothing. Files without the header are never touched.
- The generators use distinct ownership headers, so each MUST have its own output root: in a
  shared root, each generator treats the others' files as its own stale output and removes or
  replaces them.
- Formatting is produced by the emitter, not by running `rustfmt` or `protoc`. Rust uses four
  spaces; proto uses two; JSON uses two-space indentation and compact nested schemas. Output must
  be valid and compile/parse without a formatting pass.
- Docs from WIT `///` comments are carried to Rust `///` and proto `//` comments. Empty docs are
  omitted. `@unstable` and `@since` are metadata in the current 0.x line: they are carried in the model but do
  not change generated code. Docs and stability are not wire identity and may change.
- `use` aliases and `type a = b` aliases are emitted as Rust type aliases in the interface that
  names them. Neither creates a protobuf type or a lockfile member; canonical types and proto
  references resolve through the alias to the defining type.
- Unsupported constructs are refused by the subset checker before an emitter runs. An emitter
  MAY return an internal error if it still sees one.
- Worlds generate shared metadata, not traits or per-version types. They are validated and kept
  in the model, and the Rust emitter writes `worlds.rs` with each world's imports and exports
  (section 3.6).

## 2. Inputs and version layout

Generation commands take a WIT **root** containing version directories:

```text
wit/
  released
  v0.1/
    *.wit
    wire.lock
  v0.2/
    *.wit
    wire.lock
```

- Every directory named `v<major>.<minor>` is a contract version. Files and other directories
  are ignored. A root with no version directories is an error.
- All version directories in a root MUST share the package namespace and name; only the version
  may differ. A mismatch is an error.
- The package version in each directory MUST be exactly `@<major>.<minor>.0`. A mismatch is an
  error in a versioned tree.
- Two version directories MUST NOT contain the same package version.
- Versions are processed in ascending semver order.
- The generator validates the subset and the lockfile for every version before writing
  anything. A stale or invalid version fails the whole generation.
- Within each major, every minor's lockfile MUST continue the previous minor's: every previous
  entry is kept with the same number, kind, and canonical type, and a reserved entry stays
  reserved (the continuity `check --against` verifies; see
  [`lockfile.md`](lockfile.md#2-version-directories-and-release-status)). A lockfile that does
  not continue its predecessor fails the whole generation; a new major starts a fresh lockfile.
- Rust output is one module per version: `v<major>_<minor>`.
- Proto output is one file per major version: `v<major>.proto`, generated from the highest
  minor of that major. A new minor updates the same file; a new major adds a new file/package.
- `check` and `lock` operate on a single version directory; only the `rust`, `proto`, and
  `glue` commands take the root.

## 3. Rust emitter

### 3.1 Module layout

For a root with `v0.1` and `v0.2`, the output is:

```text
<out>/mod.rs
<out>/v0_1.rs
<out>/v0_2.rs
```

`mod.rs`:

```rust
// @generated by witforge; do not edit.
// source: example:plugin

pub mod v0_1;
pub mod v0_2;
```

`v0_1.rs` contains one inline module per interface and re-exports its traits:

```rust
// @generated by witforge; do not edit.
// source: example:plugin@0.1.0

pub mod types {
    // records, variants, enums, flags, aliases
}

pub mod analyzer {
    // interface-local types and the trait

    pub trait Analyzer {
        fn analyze(
            &self,
            path: ::std::string::String,
            bytes: ::std::vec::Vec<u8>,
        ) -> ::std::result::Result<
            ::std::vec::Vec<super::types::Finding>,
            ::std::string::String,
        >;
    }
}

pub use analyzer::Analyzer;
```

- Types are grouped by the interface that defines them. A `use` alias is emitted as a Rust type
  alias in the using interface's module; it does not create a second defining type or module.
  References to a type through `use` resolve to the defining interface's type.
- A trait lives in its interface module and is re-exported at the version root. If two
  interfaces map to the same trait name, generation fails with a collision diagnostic.
- Trait references to another interface use `super::<interface>::<Type>`.
- Worlds produce no module.

### 3.2 Name conversion

- Type, interface, alias, and enum/variant case names: PascalCase. Split on `-`, capitalize
  each segment, concatenate (`edit-file` -> `EditFile`).
- Field, function, parameter, flags-member, and interface-module names: snake_case. Replace
  `-` with `_` (`edit-file` -> `edit_file`).
- Use raw identifiers where Rust allows them: `type` -> `r#type`, `where` -> `r#where`.
- Names that cannot be raw get a trailing underscore: `self` -> `self_`, `Self` -> `Self_`,
  `crate` -> `crate_`, `super` -> `super_`.
- A name that would start with a digit or be empty is a contract error.
- After conversion, collisions are detected within each Rust scope: types and the interface trait
  within an interface module, members within a type, functions within a trait, traits/modules at
  the version root. A collision is a hard error naming the colliding WIT items. Names are never
  silently mangled. For example, a type named `analyzer` in interface `analyzer` collides with
  the generated `Analyzer` trait and is refused.
- Generated code uses fully qualified standard-library paths (`::std::string::String`,
  `::std::vec::Vec`, `::std::option::Option`, `::std::result::Result`) so a contract type named
  `String`, `Vec`, `Option`, or `Result` cannot shadow them.
- Type names are not re-exported at the version root, so two interfaces may define the same
  type name.

The Rust keyword and reserved-word table used by the emitter is:

```text
as, async, await, break, const, continue, crate, dyn, else, enum, extern, false, fn, for,
gen, if, impl, in, let, loop, match, mod, move, mut, pub, ref, return, self, Self, static,
struct, super, trait, true, type, unsafe, use, where, while, abstract, become, box, do,
final, macro, override, priv, try, typeof, union, unsized, virtual, yield
```

Raw identifiers are used for every name in that table except `crate`, `self`, `super`, and
`Self`, which use a trailing underscore. `_` is not a legal WIT name and is refused. The table
is tested against the compiler with a compile test so a new Rust edition keyword is not missed.

### 3.3 Derives

Every generated struct or enum gets:

```rust
#[derive(Debug, Clone, PartialEq)]
```

There is no `Eq`, `Hash`, `Default`, `Copy`, `prost`, or `#[non_exhaustive]` derive, and
fields and variants are `pub`. Conditional `Eq`/`Hash`/`Default` are declined for 0.x/1.0; the
float, Default, and frozen-version reasoning is in
[`overview.md`](overview.md#102-conditional-eqhash-and-default-evaluation-w6-003).

Serde is opt-in. With `[project.<name>.rust] serde = true` (or `--serde`), records, enums,
variants, and flags additionally derive:

```rust
#[derive(Debug, Clone, PartialEq, ::serde::Serialize, ::serde::Deserialize)]
```

The consumer must depend on `serde` with the `derive` feature. Type aliases cannot derive; their
target types do. The default output, `--no-serde`, and the existing generated API are unchanged;
`--serde` overrides a configuration that left it off, and `--no-serde` overrides one that left it
on. Floats, nested options/lists/results, and all generated structural shapes are covered by a
compile and JSON round-trip test.

### 3.4 Type mapping

| WIT | Rust |
|---|---|
| `bool` | `bool` |
| `u8`, `u16`, `u32`, `u64` | `u8`, `u16`, `u32`, `u64` |
| `s8`, `s16`, `s32`, `s64` | `i8`, `i16`, `i32`, `i64` |
| `f32`, `f64` | `f32`, `f64` |
| `string` | `::std::string::String` |
| `list<u8>` | `::std::vec::Vec<u8>` |
| `list<T>` | `::std::vec::Vec<T>` |
| `option<T>` | `::std::option::Option<T>` |
| `result<T, E>` | `::std::result::Result<T, E>` |
| `result<T, _>` | `::std::result::Result<T, ()>` |
| `result<_, E>` | `::std::result::Result<(), E>` |
| `result<_, _>` / bare `result` | `::std::result::Result<(), ()>` |
| record | `pub struct` with `pub` fields |
| variant | `pub enum` with payload variants |
| enum | `pub enum` |
| flags | `pub struct` of `pub bool` fields |
| `type a = b` | `pub type A = B;` |
| `use ... as ...` alias | `pub type Alias = DefiningType;` in the using interface module |
| named `list`/`option`/`result` | `pub type` alias |

Examples:

```rust
pub struct Span {
    pub start: u64,
    pub end: u64,
}

pub enum Applicability {
    Safe,
    Unsafe,
    Suggestion,
    Never,
}

pub enum Edit {
    Replace(Span),
    DeleteFile,
}

pub struct Caps {
    pub git: bool,
    pub environment: bool,
}

pub type Tags = ::std::vec::Vec<::std::string::String>;
```

### 3.5 Traits

- One trait per interface, named after the interface in PascalCase.
- Methods are the interface's functions, named in snake_case.
- Receiver: `&self`.
- Parameters and returns use owned mapped types exactly as in section 3.4.
- No supertraits, generics, lifetimes, or `async`.
- A function with no result returns `()`.
- The trait is object-safe: no generic methods, no `Self` returns, no borrowed parameters.
  Owned parameters remain the 0.x and 1.0 policy; the measured alternative and its trigger are in
  [`overview.md`](overview.md#101-borrowed-rust-parameter-measurement-w6-002).
- Generated traits do not promise `Send` or `Sync`; consumers may add bounds in their own
  wrapper APIs.

### 3.6 World metadata

When any version has a world, `rust` also emits a shared `worlds.rs` at the Rust output root and
declares `pub mod worlds;` in `mod.rs`:

```rust
pub struct World {
    pub name: &'static str,
    pub imports: &'static [&'static str],
    pub exports: &'static [&'static str],
}

pub mod v0_1 {
    pub const WORLDS: &[super::World] = &[ ... ];
}
```

- Every version gets a `WORLDS` constant, including an empty array when that version has no
  worlds.
- Worlds are emitted in source order; imported and exported interface names are in source order
  and are separate fields, so direction is explicit. A dependency interface is written with its
  package-qualified name, such as `example:shared/types`; a local interface keeps its bare name.
- The metadata has no runtime dependency and does not reference generated traits or types.
- `worlds.rs` is shared output: adding a version adds its module and can change the file, while
  released per-version Rust modules remain unchanged.
- A root with no worlds emits no `worlds.rs` and no `worlds` declaration.


### 3.7 Dependency modules

When the package references a named type or a world interface from a standard `deps/` package,
`rust` also emits `witforge_deps.rs` and declares `pub mod witforge_deps;` in `mod.rs`. Each dependency package is
a module named `<namespace>_<package>` and each interface is a module beneath it. Local
foreign-type references use `super::super::witforge_deps::...`; references between dependency
packages use `super::super::...`.

Unsupported dependency items that the root does not use are skipped rather than failing the
root. If the root uses an item that could not be represented, the emitter reports a missing
dependency type. See [`dependencies.md`](dependencies.md).

## 4. Protobuf emitter

### 4.1 File, package, and names

- One file per major: `<out>/v<major>.proto`; one file per dependency:
  `<out>/<namespace>.<package>.v<major>.proto`, with `-` replaced by `_` in both names.
- Package: `<namespace>.<name>.v<major>`, with `-` replaced by `_`.
- File header:

  ```proto
  // @generated by witforge; do not edit.
  // source: example:plugin@0.2.0

  syntax = "proto3";

  package example.plugin.v0;
  ```

- Every generated name derived from a user type, interface, or function is prefixed with its
  defining interface in PascalCase. Synthesized wrappers use the `Witforge` prefix, and `Empty`
  is shared. Examples:

  ```proto
  message TypesSpan { ... }
  message TypesFinding { ... }
  enum TypesApplicability { ... }
  message AnalyzerAnalyzeRequest { ... }
  message AnalyzerAnalyzeResponse { ... }
  enum AnalyzerMethod { ... }
  ```

- The shared `Empty` message is `message Empty {}` at the package root. It is used for
  payload-less variant cases and for missing `result` payloads.
- Generated names, oneof names, field names, enum values, method ids, wrappers, and reserved
  names are collision-checked across the whole proto package. A collision is a hard error.
- Proto package components are the WIT namespace and name with `-` replaced by `_`. If that
  mapping collides with another generated package or is not a valid proto identifier, generation
  fails.
- Proto has no raw identifiers. The emitter keeps a proto keyword/reserved-word table; a
  converted message, enum, wrapper, enum-value, package, or other type-position name that is a
  proto keyword or otherwise invalid is a hard error naming the WIT item. Field-position names
  may be proto keywords because protobuf accepts them there; the real alint contract depends on
  a field named `message`. The table is covered by golden tests. Silent suffixing or renaming is
  not allowed because it would change proto3-JSON names unpredictably.

### 4.2 Messages and enums

- A record becomes a message. Field names are snake_case; field numbers come from the lockfile.
  Fields carry `//` docs. Record fields are required by WIT; required scalar/string/bool/float/
  enum/bytes fields use proto3 `optional`, and the glue presence-checks every required field.
- A variant becomes a message with a `oneof witforge_value`. Each case is a field named in
  snake_case; a payload case uses `singular(payload)` from section 4.3, so a list or option
  payload is wrapped; a payload-less case uses `Empty`. Numbers come from the lockfile. A case
  whose converted field name is `witforge_value` collides with the oneof name and is a hard
  error.
- An enum becomes a proto enum. The first value is `<ENUM_NAME>_UNSPECIFIED = 0`; cases start at
  the lockfile numbers and use `<ENUM_NAME>_<CASE>` in UPPER_SNAKE. A case that maps to
  `UNSPECIFIED` is an error. Enums are closed: zero and unknown values are decode errors in the
  glue.
- Flags become a message of `bool` fields, numbered from the lockfile.
- A named record/variant/enum/flags type is a message/enum named
  `<InterfacePascal><TypePascal>`.
- A `type a = b` alias is inlined.
- A named `list`, `option`, or `result` does not create a separate alias type in proto; its
  structural projection is used at each site. When that projection requires a message (a named
  result, or an option of a list/option), the message is named as described in section 4.4.

### 4.3 Type mapping

The table gives the proto value type. Required scalar/string/bool/float/enum/bytes occurrences
add `optional`; required message fields use message presence; repeated fields use `repeated`.
See Presence below for the required/optional distinction.

| WIT | proto |
|---|---|
| `bool` | `bool` |
| `u8`, `u16`, `u32` | `uint32` |
| `u64` | `uint64` |
| `s8`, `s16` | `sint32` |
| `s32` | `sint32` |
| `s64` | `sint64` |
| `f32`, `f64` | `float`, `double` |
| `string` | `string` |
| `list<u8>` | `bytes` |
| `list<T>` | `repeated singular(T)` |
| `option<T>` (scalar, string, enum) | `optional T` |
| `option<T>` (record, variant, flags, result) | message field (presence) |
| `option<list<u8>>` | `optional bytes` |
| `option<list<T>>`, `option<option<T>>` | synthesized wrapper message |
| `result<T, E>` | message with `oneof value { singular(T) ok = 1; singular(E) err = 2; }` |
| `result<T, _>` | `oneof value { singular(T) ok = 1; Empty err = 2; }` |
| `result<_, E>` | `oneof value { Empty ok = 1; singular(E) err = 2; }` |
| bare `result` | `oneof value { Empty ok = 1; Empty err = 2; }` |
| record | message |
| variant | message with a `oneof witforge_value` |
| enum | enum |
| flags | message of `bool` fields |
| `type a = b` | inlined |
| named `list`/`option`/`result` | structural projection; named message when required (section 4.4) |

#### Presence

Proto3 scalar, string, bool, float, enum, and `bytes` fields have implicit defaults. To preserve
WIT’s required-field semantics, every **required** occurrence of one of those types in a record
field, request parameter, or response result whose type is one of those forms is emitted with
`optional`, and the glue rejects absence with `MissingField`:

```proto
message TypesSpan {
  optional uint64 start = 1;
  optional uint64 end = 2;
}
```

The schema alone cannot tell a required `optional T` from an `option<T>` field; the model does,
and the glue applies different rules:

- required `optional T`: `None` is `MissingField`; `Some(value)` is validated and unwrapped;
- WIT `option<T>`: `None` is `None`; `Some(value)` is validated;
- required `bytes` (`list<u8>`) is `optional bytes`; `None` is `MissingField`;
- `option<list<u8>>` is also `optional bytes`, but `None` is a valid `None`;
- a required `repeated` field (`list<T>`) may be empty; absence and empty are the same and both
  are valid;
- a required message field uses message presence; `None` is `MissingField`;
- oneof members (result sides and variant payloads) do not use `optional`; selecting the oneof
  member provides presence, and an unset/unknown oneof is `UnknownCase`.

Requiredness is carried by the model and the generated glue, not by the proto schema alone: a
consumer that uses the `.proto` without witforge’s glue must enforce required presence itself.

Nested shapes are defined by two recursive mappings:

- `direct(T)` is the type used for a normal message field. It may be repeated or optional. For a
  required scalar/string/bool/float/enum/bytes occurrence, the emitter adds `optional` as
  described under Presence; `direct(T)` names the value type.
- `singular(T)` is a singular, non-optional type usable as a `oneof` member or a repeated
  element.

`direct(T)`:

- primitives, `string`, `enum`, `record`, `variant`, `flags`, and `result` use their mapped
  scalar/message/enum type;
- `list<u8>` is `bytes`;
- `list<T>` is `repeated singular(T)`;
- `option<U>` is:
  - `optional U` for scalar, `string`, or enum;
  - `optional bytes` for `option<list<u8>>`;
  - a message field of `direct(U)` for a record, variant, flags, or result;
  - a message field of `singular(U)` for `U = list<T>` (where `T` is not `u8`) or
    `U = option<V>`. Field presence supplies the outer `None`.

For a direct option whose inner type is a list or option, the `singular` wrapper is used as a
message field; an absent field is `None`, and a present field is `Some(...)`. A named
`option<...>` type names that wrapper as described in section 4.4.

`singular(T)`:

- primitives, `string`, `bytes`, enum, record, variant, flags, and result are already singular;
  use their mapped type;
- `list<u8>` is `bytes`;
- `list<T>` becomes a wrapper message with `repeated singular(T) values = 1`;
- `option<U>` becomes a wrapper message:
  ```proto
  message <Wrapper> {
    oneof value {
      Empty none = 1;
      <singular(U)> some = 2;
    }
  }
  ```

Consequences:

- `list<list<u8>>` as a normal field is `repeated bytes`; as a `oneof` payload it is a wrapper
  containing `repeated bytes values = 1`.
- `list<option<T>>` as a normal field is `repeated <option wrapper>`.
- `option<list<u8>>` as a normal field is `optional bytes`; as a `oneof` payload it is an
  option wrapper whose `some` field is `bytes`.
- `option<list<T>>` as a normal field is the list wrapper used as a message field (absent =
  `None`, present = `Some(list)`); as a `oneof` payload it is an option wrapper around that list
  wrapper.
- `option<option<T>>` as a normal field is the option wrapper used as a message field; as a
  `oneof` payload it is an option wrapper around that inner option wrapper.
- `result<T, E>` uses `singular(T)` and `singular(E)` for its oneof members, and a missing
  payload uses `Empty`.
- Variant cases use `singular(payload)`; a payload-less case uses `Empty`.
- Request fields and the response `result = 1` field use `direct(...)`, so a parameter or result
  that is a list can be repeated directly.

Wrapper field names and numbers are fixed (`values = 1`, `value = 1`, `none = 1`, `some = 2`,
`ok = 1`, `err = 2`) and are not locked; wrappers affect generated code and JSON shape only.

### 4.4 Wrapper names

Anonymous wrappers are top-level messages with a reserved `Witforge` prefix and a structural
name derived from the canonical type:

- primitives use PascalCase WIT names (`Bool`, `U64`, `S64`, `F32`, `String`);
- a named type uses its interface and type in PascalCase (`TypesSpan`);
- `list<T>` is `ListOf<T>`, `option<T>` is `OptionOf<T>`;
- `result<ok,err>` is `ResultOf<Ok>And<Err>`, with `_` rendered as `Empty`;
- nested expressions concatenate, for example `ListOfListOfTypesSpan`,
  `OptionOfListOfTypesSpan`, and `ResultOfListOfTypesFindingAndString`.

```proto
message WitforgeListOfTypesSpan {
  repeated TypesSpan values = 1;
}

message WitforgeOptionOfListOfTypesSpan {
  oneof value {
    Empty none = 1;
    WitforgeListOfTypesSpan some = 2;
  }
}

message WitforgeListOfTypesFinding {
  repeated TypesFinding values = 1;
}

message WitforgeResultOfListOfTypesFindingAndString {
  oneof value {
    WitforgeListOfTypesFinding ok = 1;
    string err = 2;
  }
}
```

Naming rules for named types:

- A named record, variant, enum, or flags type uses its interface-prefixed message/enum name,
  and that message is already singular.
- A named `result` uses its interface-prefixed result message and is used directly in oneof
  contexts.
- A named `list<T>` is inlined as `repeated singular(T)`; it has no named message. A singular
  form uses the anonymous list wrapper (or `bytes` for `list<u8>`).
- A named `option<...>` has a named direct message only when its direct projection needs a
  wrapper, that is `option<list<T>>` (T not `u8`) or `option<option<V>>`. In that case the
  wrapper used by the direct projection (the list wrapper or the inner option wrapper) takes the
  named type's interface-prefixed name and is used as a message field for normal occurrences.
- A named option in a oneof or repeated context uses an anonymous `WitforgeOptionOf...` wrapper
  around its direct representation; if the direct representation is already the named option
  wrapper, the anonymous wrapper is named for that wrapper and has it as its `some` field.
- Named options of scalar, string, enum, bytes, record, variant, flags, or result have no direct
  wrapper; their singular form is an anonymous option wrapper around the mapped payload type,
  named structurally from that payload.
- Anonymous shapes always use the `Witforge...` names.
- Identical anonymous shapes share one wrapper within the package.
- A wrapper name collision with a user type or another wrapper is a hard error.

### 4.5 Functions

For each interface function:

```proto
message AnalyzerAnalyzeRequest {
  optional string path = 1;      // locked: analyzer#analyze.path
  optional bytes bytes = 2;      // locked: analyzer#analyze.bytes
}

message AnalyzerAnalyzeResponse {
  WitforgeResultOfListOfTypesFindingAndString result = 1;
}

enum AnalyzerMethod {
  ANALYZER_METHOD_UNSPECIFIED = 0;
  ANALYZER_METHOD_ANALYZE = 1;  // locked: analyzer.analyze
}
```

- Request fields are the parameters, in WIT order, numbered from the lockfile; names are
  snake_case. A parameterless function gets an empty request message.
- Response always has exactly one field, `result = 1`, whose type is the mapped function
  result. A function with no result gets an empty response message. The field number is fixed
  and is not locked; the method entry's result type catches changes.
- Each interface gets a method-id enum `<InterfacePascal>Method`; zero is `UNSPECIFIED`;
  functions use their lockfile numbers and `<INTERFACE>_METHOD_<FUNCTION>` names. A function
  that maps to `UNSPECIFIED` is an error.
- Request/response message names are `<InterfacePascal><FunctionPascal>Request` and
  `Response`.

### 4.6 Reserved members

For every reserved lockfile entry, the containing message/enum emits reserved numbers and
reserved names as separate statements:

```proto
reserved 3, 4;
reserved "old_field", "older_field";
```

- Numbers are emitted in ascending order; names are sorted lexicographically. Proto does not
  allow mixing numbers and names in one `reserved` statement.
- Record/flag/variant fields reserve their message field numbers and snake_case names.
- Enum cases reserve their enum numbers and UPPER_SNAKE names.
- Method ids reserve their enum numbers and UPPER_SNAKE names.
- Request parameters of a live function reserve their request field numbers and snake_case names.
- Request/response messages of a removed function are no longer emitted; proto has no
  message-name reservation, and the reserved method id prevents wire reuse.
- If a new WIT member would map to a reserved proto name, generation fails; the contract must
  use a new name.

### 4.7 Proto3 JSON

The generated schema is the source of proto3-JSON behavior; pbjson derives the JSON names. In
particular:

- field names use lowerCamelCase JSON names;
- `u64`/`s64` are decimal strings;
- `list<u8>` is base64;
- non-finite floats are `"NaN"` / `"Infinity"` strings;
- enums are name strings;
- `result` is `{"ok": ...}` or `{"err": ...}`;
- option presence is absence or `null` for message fields, and absence for proto3 `optional`;
  required `optional`/message fields use the same JSON shapes, but the glue rejects
  absence/null as `MissingField`.

The glue tests in section 6 must cover these rules.

## 5. Output, `--check`, and CLI

### 5.1 Commands

```text
witforge check <version-dir> [--lock <path>] [--against <path> | --first]
                            [--released <path>]
witforge lock  <version-dir> [--lock <path>] [--against <path> | --first]
                            [--released <path>]
witforge rust  [<wit-root>] [--out <dir>] [--config <file>] [--project <name>]
               [--check] [--released <path>]
               # also writes convert.rs for adjacent versions
witforge proto [<wit-root>] [--out <dir>] [--config <file>] [--project <name>]
                            [--check] [--released <path>]
witforge schema [<wit-root>] [--out <dir>] [--config <file>] [--project <name>]
                            [--check] [--released <path>]
witforge glue  [<wit-root>] [--out <dir>] [--plain-root <path>] [--proto-root <path>]
                            [--config <file>] [--project <name>] [--check]
                            [--released <path>]
```

- `check` and `lock` take one version directory; the default lockfile is
  `<version-dir>/wire.lock`. A directory named `v<major>.<minor>` must hold that package version,
  as for the generators ([`lockfile.md`](lockfile.md) section 2); any other name is an ad-hoc
  directory.
- `rust`, `proto`, `schema`, and `glue` take the WIT root and require every version directory to
  be valid and locked, and every minor's lockfile to continue the previous minor's in its major.
  The positional root and output flags may instead be resolved from a `--config` project
  (section 11); CLI flags override the configuration.
  `rust` also emits `convert.rs` (section 9) when the root has two or more versions, and
  `worlds.rs` (section 3.6) when any version has a world; conversion generation refuses an
  evolution step that a default-only adapter cannot express.
- `glue` additionally requires `--plain-root` and `--proto-root`; it covers the highest minor of
  each major, so older plain modules get no glue. It refuses every contract `proto` refuses
  (section 7.1).
- The released manifest default is `<version-dir>/../released` for `check`/`lock`, and
  `<wit-root>/released` for generation. Every command validates the manifest: an explicitly
  given missing manifest or a malformed one is an error (exit `2`). Generation reproduces
  released versions without modifying them, so for `rust`, `proto`, `schema`, and `glue` the
  manifest only has to be valid.
- `--first` and `--against` are mutually exclusive. They are defined in
  [`lockfile.md`](lockfile.md).
- Generation creates the output directory when it is missing. The output root MUST NOT be the WIT
  root or inside it (which includes every version directory); such a path is refused. Both paths
  are resolved before the comparison: the WIT root and the longest existing prefix of the output
  root are canonicalised, and the rest of the output root is normalised lexically, so `..`
  components and symlinks cannot reach the WIT root. `--check` requires the output directory to
  exist and scans only the output root (not subdirectories) for generated-header files.
- `--check` writes nothing. It fails if an expected file is missing or differs, if a
  generated-header file in the output root is not expected, or if an expected path is one that
  generation refuses to write (see below), so `--check` and generation agree on what needs
  fixing. It ignores files without the header at other paths. It reads only regular files, so a
  FIFO or a device at an expected path is reported without being opened. Recognising the header
  reads only the start of each file, as bytes, so a file that is not UTF-8 text (a `.DS_Store`,
  an image) is ignored like any other file without the header.
- Generation removes stale generated files in the output root and never touches files without
  the header. It validates every version before writing the first file; a failed run may leave a
  partial set, and rerunning after fixing the input completes it.
- Generation never replaces a symlink, writes through one at an expected file's path, or
  overwrites a file it does not own. Before anything is written or removed, every expected path
  that already exists must be a regular file that starts with the header; a symlink, a directory
  or other non-regular file, or a file without the header fails generation with exit `2` and
  changes nothing. `--check` reports each of them as drift. The output root itself and its
  parents may be symlinks; the output-root rule above resolves them. No version directory is a
  symlink ([`lockfile.md`](lockfile.md) section 2), so no output root can resolve into one.
- A consumer's CI SHOULD freeze the committed per-version Rust module and `wire.lock` for a
  released version together with the `wit/released` entries. `mod.rs`, `convert.rs`, `worlds.rs`,
  the per-major `v<major>.proto`, and the per-major glue module are shared across versions and may
  change when a new minor is added; their released members are protected by the lockfile,
  `--check`, and proto compatibility checks. `--check` is the tool-side verification.
- witforge's CI runs `ci/check-generated.sh` for every emitter (it generates the fixtures
  into a scratch directory and checks that output with `--check`, so it covers witforge itself; a
  consumer runs each generator's `--check` against its own committed output) and
  `ci/check-release-freeze.sh` for released directories and manifest entries. The aplan plan is
  checked in CI by the `plan` job with pinned published aplan 0.5.2.
  `ci/check-buf.sh` is an optional extra `buf breaking` check for consumers that use it; the
  lockfile remains the normative wire gate.
- Exit codes: `0` success; `1` contract, lockfile, or output drift; `2` usage, IO, parse,
  released-directory refusal, or internal error. Every command follows this scheme. For `rust`,
  `proto`, `schema`, and `glue`, a version that fails validation (subset violations, a version or package
  mismatch, a lockfile entry of another package, a stale or discontinuous lockfile, a
  generated-name collision, an evolution step that `convert.rs` cannot express, for `glue` also
  one in the protobuf schema) exits `1`, as does
  `--check` drift; a WIT package or lockfile that
  cannot be read or parsed, an invalid module root, a symlinked version directory or one whose
  name has a sign or leading zeros, an output root inside the WIT root, an expected output path
  that generation refuses, and an internal error exit `2`. The library reports the first class
  as a `witforge::ContractError` in the error chain (`witforge::is_contract_error`); the emitters
  mark each contract violation where they find it, so an internal error is never reported as
  one.
- The CLI uses `clap`; every command supports `--help`, and the binary supports `--version`.

### 5.2 Output files

| Command | Expected files |
|---|---|
| `rust` | `mod.rs`, `v<major>_<minor>.rs` for every version, `convert.rs` when there are two or more versions, `worlds.rs` when any version has a world, `witforge_deps.rs` when the package uses standard `deps/` types |
| `proto` | `v<major>.proto` for every major, `<namespace>.<package>.v<major>.proto` for every dependency |
| `schema` | `v<major>_<minor>.schema.json` for every version, `<namespace>.<package>.v<major>.schema.json` for every dependency |
| `glue` | `mod.rs`, `v<major>.rs` for every major, `witforge_deps.rs` when the package has dependencies |

Rust per-version files contain inline interface modules. `mod.rs` declares every version module
in ascending order and, when present, `witforge_deps`, `convert`, and `worlds`. `witforge_deps.rs`
contains the generated dependency modules (section 3.7). `convert.rs` contains one module per
adjacent version pair in each direction (section 9); `worlds.rs` contains per-version world
metadata (section 3.6). Proto files are generated from the highest minor in each major; each
dependency schema has a sanitized `<namespace>.<package>.v<major>.proto` name and is imported
only by files that reference it. JSON Schema files are generated for every version and contain
all named definitions (section 10). Dependency schemas are emitted separately and referenced by
relative file path; keep the generated schema files together when resolving foreign definitions.
Glue files are generated from the highest minor in each major and reference its plain module and
the shared dependency glue module.

## 6. Testing requirements

- Golden tests for every mapping row, with committed expected `.rs`, `.proto`, and glue files.
- At least one generated Rust/glue fixture is compiled as part of the test suite; at least one
  generated proto fixture is parsed/compiled with `protox` or `protoc`.
- Golden tests cover docs, keyword escaping, name collisions, aliases, named
  list/option/result, nested wrappers, direct-vs-singular wrapper forms for named options,
  one-sided results, payload-less variants, flags, and reserved members.
- Dependency tests: a local package importing pinned dependency types, aliases, lists, options,
  results, enums, variants, cross-dependency references, and hyphenated package names; generated
  Rust and protobuf compile; a dependency's unused unsupported item does not break the root; and
  version conversion copies a pinned foreign value.
- Determinism tests: two runs produce byte-identical output; LF only; no timestamps.
- `--check` tests: missing, changed, extra generated, and unrelated files, including files that
  are not UTF-8 text, and an expected path that is a symlink, a directory, a FIFO, or a file
  without the header.
- Output-root tests: the WIT root and anything inside it are refused, also when reached through
  `..` components or symlinks; an expected path that is a symlink, a directory, or a file without
  the header is refused before anything changes.
- Version-directory tests: a symlinked version directory is refused by every command, with
  nothing written even when the output root is that link, and a name with a sign or leading zeros
  is refused.
- Continuity tests: a minor whose lockfile does not continue the previous minor's fails every
  generator; a new major starts fresh.
- CLI integration tests that run the built binary with `std::process::Command` in directories
  under `std::env::temp_dir()`, for `rust`, `proto`, `schema`, `glue`, and `--check`.
- Lockfile property tests with `proptest`.
- Protobuf glue round-trip tests (Rust value -> proto -> Rust; proto -> JSON -> proto -> Rust)
  through the generated glue and helpers, including dependency values and dependency interface
  functions.

## 7. Protobuf glue

The `glue` emitter converts between the plain Rust types and the `prost`/`pbjson` types. It is
generated from the highest minor of each major; older plain modules remain for native adapters
and the later version-conversion layer.

### 7.1 Coverage and input

- Glue covers every named type in the highest minor of each major, including records, variants,
  enums, flags, aliases, `use` aliases, named `list`/`option`/`result`, and named structural
  forms.
- Glue covers every interface function in that version, and every dependency type and interface
  function under the shared dependency glue module.
- Older minors get no glue module; they are not the proto schema’s source version.
- The emitter uses the same model, canonical types, collision rules, and naming conversion as
  the Rust and proto emitters. It converts to and from the prost types generated from the
  protobuf schema, so it refuses every contract the proto emitter refuses, with the same
  diagnostic and exit `1`: a record `f-request` beside a function `f`, whose request message is
  also `IFRequest`, fails `glue` as it fails `proto`, although glue's own names do not collide.
  WIT docs are carried to glue module/function docs where they describe the type or function;
  synthesized helpers get a short doc comment.
- A type or function that the subset checker refuses never reaches glue.

### 7.2 CLI, output layout, and module paths

```text
witforge glue <wit-root> --out <dir> \
  --plain-root <rust-module-path> \
  --proto-root <rust-module-path> \
  [--check] [--released <path>]
```

- `--plain-root` is the Rust module that contains `v<major>_<minor>` modules and, for a contract
  with dependencies, `witforge_deps`, for example `crate::generated`.
- `--proto-root` is the Rust module that contains the root protobuf module and dependency
  modules, for example `crate::proto`. Without dependencies the root is
  `<proto-root>::v<major>`; with dependencies it is
  `<proto-root>::<root-namespace>::<root-package>::v<major>`.
- Both roots are required. The tool does not guess them.
- Each root MUST be a valid Rust module path: `crate`, `self`, `super`, or identifiers (including
  raw identifiers) separated by `::`; empty segments, trailing `::`, generics, and whitespace are
  errors.
- Generated references:
  - plain local: `<plain-root>::v<major>_<minor>::...`
  - plain dependency: `<plain-root>::witforge_deps::<namespace>_<package>::...`
  - proto local: `<proto-root>::v<major>::...` without dependencies, or
    `<proto-root>::<namespace>::<package>::v<major>::...` with dependencies
  - proto dependency: `<proto-root>::<dependency-namespace>::<dependency-package>::v<major>::...`
- Output:

  ```text
  <out>/mod.rs      // GlueError, v0, v1, and witforge_deps when needed
  <out>/v0.rs
  <out>/v1.rs
  <out>/witforge_deps.rs
  ```

- One glue module per major, matching the one-proto-per-major rule. `mod.rs` declares the major
  modules in ascending order.
- `--check`, generated-header ownership, stale-file removal, LF-only output, and the rule that
  the output root must not be the WIT root or inside it are the same as the Rust/proto emitters.
- A root with no version directories is an error.
- Glue `v<major>.rs` is shared across the major’s minors and may change when a new minor is
  added. Released per-version plain Rust modules are frozen; glue is current-schema output and
  is verified by `--check`, not frozen per minor.

### 7.3 Module layout

`mod.rs` defines the root error type and declares the major modules:

```rust
pub enum GlueError { ... }

pub mod v0;
pub mod witforge_deps; // when the package has dependencies
```

`v0.rs` mirrors local interfaces:

```rust
pub mod types {
    pub mod span { /* to_proto / from_proto */ }
}

pub mod analyzer {
    pub mod finding { /* type conversions */ }
    pub mod functions {
        pub mod analyze { /* request/response helpers */ }
    }
}
```

`witforge_deps.rs` mirrors dependency packages and interfaces:

```rust
pub mod example_shared {
    pub mod types {
        pub mod thing { /* to_proto / from_proto */ }
        pub mod functions { /* dependency interface functions */ }
    }
}
```

- Types are direct children of their interface module: `glue::types::span`.
- Functions live under a `functions` container: `glue::analyzer::functions::analyze`.
- Dependency modules use the same shape under
  `glue::witforge_deps::<namespace>_<package>::<interface>`.
- The converted module name `functions` is reserved for that container; a type whose converted
  name is `functions` is a hard error.
- Type and function module names use the Rust snake_case conversion and collision rules. A
  collision is a hard error.
- `GlueError` is reachable as `<glue-root>::GlueError`. The emitter imports it with
  `use super::GlueError;` in every module that names it (version, interface, `functions`, type,
  and function modules), so generated signatures can name `GlueError` directly without deep
  `super::` chains. Generated modules never define a user item named `GlueError` in the same
  scope.

### 7.4 `GlueError`

```rust
#[derive(Debug, Clone, PartialEq, Eq)]
#[non_exhaustive]
pub enum GlueError {
    IntegerOutOfRange {
        field: &'static str,
        value: i64,
    },
    MissingField {
        field: &'static str,
    },
    UnknownEnumValue {
        enumeration: &'static str,
        value: i32,
    },
    UnknownCase {
        message: &'static str,
    },
    InvalidState {
        message: &'static str,
    },
}
```

- One error type is shared by all majors in the glue root.
- `field`, `enumeration`, and `message` carry canonical WIT identities where possible.
- `MissingField` covers a required proto3 `optional` scalar/string/bool/float/enum/bytes value
  and a required message field.
- `Display` names the failing field/type and the reason; `std::error::Error` is implemented.
- `#[non_exhaustive]` allows a new decode rule to add a variant without breaking exhaustive
  matches.
- No `anyhow`, `thiserror`, `serde_json`, or other runtime dependency is used.
- `from_proto`, `from_request`, and `from_response` return `Result<_, GlueError>`.
- `to_proto`, `to_request`, and `to_response` are infallible.
- JSON conversion errors are not part of `GlueError` (section 7.7).

### 7.5 Type conversions

One module per named type:

```rust
pub mod span {
    pub fn to_proto(
        value: &<plain-root>::v0_2::types::Span,
    ) -> <proto-root>::v0::TypesSpan;

    pub fn from_proto(
        value: <proto-root>::v0::TypesSpan,
    ) -> Result<<plain-root>::v0_2::types::Span, GlueError>;
}
```

- `to_proto` takes a reference and is infallible.
- `from_proto` takes the owned proto value and is fallible.
- The proto type is the named type’s **direct** projection:
  - record/variant/flags → the named message;
  - enum → the named enum;
  - result → the named result message;
  - named `option<list>` / `option<option>` → its named direct wrapper message;
  - named `list<T>` → the direct repeated representation, for example
    `::std::vec::Vec<ProtoT>`;
  - named `option<T>` → `::std::option::Option<ProtoT>` for singular projections, or the direct
    wrapper message as a field for list/option projections;
  - alias / `use` alias → the target’s direct proto type.
- A `to_proto` for an alias or a structural named type delegates to the target conversion or
  maps elements/options.
- Anonymous `list`/`option`/`result` shapes have no module; the containing field, variant case,
  result side, or function helper converts them inline using the same rules.
- The module per named type is generated even when its direct projection is a scalar, `Vec`, or
  `Option`, so every named type is addressable. Trivial functions are acceptable.
- A field, list element, or oneof payload uses the direct or singular projection required by
  section 4.3. The named type modules expose the **direct** conversion; a parent conversion that
  needs a singular oneof/repeated-element form wraps the direct value in the required wrapper.
  This keeps one public conversion pair per named type while still handling every nested shape.
- Conversion rules:
  - in the encode direction, every required proto3 `optional` scalar/string/bool/float/enum/bytes
    field is set to `Some`, required message fields are set, and required `repeated` fields map
    to `Vec`; a required value is never encoded as absent;
  - `u8`/`u16`/`s8`/`s16` are range-checked on decode (`IntegerOutOfRange`);
  - closed enums reject zero and unknown values (`UnknownEnumValue`);
  - a required `optional` scalar/string/bool/float/enum/bytes field with `None` is
    `MissingField`; an `option<T>` field with `None` is `None`;
  - a required message field with `None` is `MissingField`; an `option<message>` field with
    `None` is `None`;
  - a required `repeated` field may be empty; absence and empty are both valid;
  - a required `optional bytes` field (`list<u8>`) with `None` is `MissingField`;
  - an unset or unknown variant/result oneof is `UnknownCase`;
  - an invalid option wrapper state is `InvalidState`;
  - list elements and option payloads recurse through the same rules;
  - `flags` bools, `list<u8>` bytes, and nested wrappers follow section 4.3.
- The glue conversion is the only place that applies these rules; the proto schema itself does
  not encode them.

### 7.6 Function helpers

Under `<interface>::functions`, one module per function. For a function with one parameter and
one result:

```rust
pub mod analyze {
    pub const METHOD: <proto-root>::v0::AnalyzerMethod =
        <proto-root>::v0::AnalyzerMethod::Analyze;

    pub fn to_request(
        path: &::std::string::String,
        bytes: &::std::vec::Vec<u8>,
    ) -> <proto-root>::v0::AnalyzerAnalyzeRequest;

    pub fn from_request(
        value: <proto-root>::v0::AnalyzerAnalyzeRequest,
    ) -> Result<
        (::std::string::String, ::std::vec::Vec<u8>),
        GlueError,
    >;

    pub fn to_response(
        value: &::std::result::Result<
            ::std::vec::Vec<...>,
            ::std::string::String,
        >,
    ) -> <proto-root>::v0::AnalyzerAnalyzeResponse;

    pub fn from_response(
        value: <proto-root>::v0::AnalyzerAnalyzeResponse,
    ) -> Result<
        ::std::result::Result<::std::vec::Vec<...>, ::std::string::String>,
        GlueError,
    >;
}
```

Arity rules:

- `to_request`: one reference argument per parameter, or no arguments.
- `from_request`: returns `()` for no parameters, the direct value for one, or a tuple for
  several.
- `to_response`: takes a reference to the plain result, or no arguments for no result.
- `from_response`: returns `()` for no result, or the direct result for one result.
- `METHOD` is the proto method-id enum value; the method id is locked by the lockfile, while the
  enum’s zero `UNSPECIFIED` value is not.
- Request parameters that are required scalars/strings/bytes/enums are proto3 `optional`;
  `to_request` sets `Some`, and `from_request` reports `MissingField` for `None`. `option<T>`
  parameters may be `None`. Required message parameters use message presence; required `list<T>`
  parameters may be empty.
- A required scalar/string/bytes/enum response result is proto3 `optional`; `to_response` sets
  `Some`, and `from_response` reports `MissingField` for `None`. An `option<T>` result may be
  `None`. Required message results use message presence; required `list<T>` results may be empty.
- Request parameter names use the Rust snake_case conversion and keyword rules; field numbers
  are the lockfile’s parameter numbers.
- Response uses the generated response message with `result = 1`.
- Function module names use the Rust snake_case conversion; a collision is a hard error.

### 7.7 Proto3-JSON and binary encoding

- Glue has no JSON or binary encoding helpers.
- Consumers use `prost::Message::encode`/`decode` for the protobuf binary form.
- Consumers use the `pbjson`-generated serde impls and their JSON library for proto3-JSON.
- Glue tests use those same paths: plain → proto → binary/JSON → proto → plain.
- The proto3-JSON rules are the generated schema’s rules: lowerCamelCase names, `u64`/`s64`
  decimal strings, bytes as base64, non-finite floats as strings, enums as names, `result` as
  `ok`/`err`, and option presence as absence/null or absence. A required `optional`
  scalar/string/bytes/enum field that is absent or null is rejected by the glue as
  `MissingField`; an `option<T>` field may be absent/null. Required message fields are
  presence-checked; required `repeated` fields may be empty.

### 7.8 Testing requirements

- Golden files for type conversions, request/response helpers, and `GlueError` display.
- Compile at least one glue module against generated plain and prost types.
- Round-trip every named type and every function helper through prost and proto3-JSON.

  unknown oneof case, invalid option state.
- Presence tests: required `optional` scalars/strings/bytes/enums reject absent/null;
  `option<T>` accepts them; required message fields reject absence; required `repeated` fields

- Arity tests for zero, one, and many parameters/results.
- Alias, `use` alias, named list/option/result, one-sided result, and nested wrapper coverage.
- `--check`, stale-file, and module-path validation tests.
- A contract the proto emitter refuses is refused by glue too.
- A released per-version plain module remains frozen while glue for its major updates with a new
  minor.
- Version conversions: old-to-new and new-to-old for every adjacent pair, defaulted additions,
  removed/retyped members, variants, enums, flags, aliases, named structural types, and the

## 9. Version-to-version conversions

`rust` writes `convert.rs` beside the per-version modules when the WIT root has two or more
version directories. It is shared output: `mod.rs` declares `convert`, and the file carries the
same generated header, LF-only rule, ownership checks, stale-file removal, and `--check`
behavior as the Rust files. Adding a minor updates `convert.rs`; released per-version modules do
not change.

### 9.1 Module layout and API

For every adjacent pair of version directories in ascending order, including a major-version
boundary, the emitter writes one module per direction:

```rust
pub enum ConversionError {
    MissingMember { path: &'static str },
    UnknownCase { path: &'static str, case: &'static str },
}

pub mod v0_1_to_v0_2 {
    #[allow(unused_imports)]
    use super::super::{ v0_1 as __witforge_from, v0_2 as __witforge_to };

    pub mod types {
        pub fn user(
            value: &super::__witforge_from::types::User,
        ) -> Result<super::__witforge_to::types::User, super::super::ConversionError>;
    }
}
```

The reverse direction has its own module, `v0_2_to_v0_1`, and the same functions with source and
target swapped. A function is named with the Rust snake_case conversion of the source type's WIT
name. A function-name collision in one interface is a contract error. Only interfaces and named
types present in both versions get functions; a removed interface or type has no adapter, and
the host must drop it or use a different type.

Every conversion takes a reference and returns
`Result<Target, ConversionError>`. Conversions are fallible in both directions because a later
version may remove a case or a required member. `MissingMember` names the canonical WIT member
path that the source version cannot supply, such as `types/user.old-field`; `UnknownCase` names
the type and case that the target version does not have. Both carry `'static` canonical WIT
identities. `ConversionError` implements `Display` and `std::error::Error`; it is
`#[non_exhaustive]` so a conversion rule can be added without breaking exhaustive matches.

### 9.2 Old-to-new rules

The source is the older version and the target is the newer one.

- A record field present in both versions converts recursively. Its name and type must be
  unchanged; a changed type is a contract error.
- A field added by the newer version is defaulted only when its type is `option<T>`, `list<T>`,
  or a named alias/structural type that resolves to one: `option` defaults to `None`, `list` to
  an empty vector. A required addition that is not defaultable is a contract error, so an
  author must add a defaultable member instead of changing an existing shape.
- A field removed by the newer version is dropped. The old value is not represented in the new
  type.
- A record field whose name changes is a removal plus an addition; the addition follows the
  default rule. The old value is not carried over, because WIT names are identity.
- A variant or enum case present in both versions converts (and a payload converts recursively).
  A case removed by the newer version makes that source value `UnknownCase`. A case added by the
  newer version is simply unreachable from an older value.
- A flags member present in both versions keeps its boolean. A flag added by the newer version is
  `false`; a flag removed by the newer version is dropped.
- A named alias or named structural `list`/`option`/`result` converts through its target type.
  A named type that changes kind, a case whose payload presence changes, and a type whose
  structural shape changes are contract errors; evolution requires a new type or member.
- An interface, type, or case that exists only in the newer version has no old-to-new adapter.

### 9.3 New-to-old rules

The source is the newer version and the target is the older one.

- A field present in both versions converts recursively under the same type-identity rule.
- A field added by the newer version and absent from the older version is dropped; the older
  type has nowhere to put it.
- An older field removed by the newer version is defaulted when its type is defaultable
  (`option<T>` to `None`, `list<T>` to empty). If it is required, the conversion returns
  `MissingMember` with that field's canonical path; it never invents a scalar or message value.
- A variant or enum case added by the newer version makes that source value `UnknownCase`. A case
  removed by the newer version is unreachable in this direction.
- A flag added by the newer version is dropped; an older flag removed by the newer version is
  `false`.
- Aliases, named structural types, and nested payloads follow the same recursive rules. Kind,
  payload-shape, and type changes are contract errors of the conversion emitter, not silent
  lossy adapters.

### 9.4 Testing requirements

- Generate and compile conversions for a root with two versions, including records, variants,
  enums, flags, aliases, named `list`/`option`/`result`, and direct `list`/`option`/`result`
  fields.
- Exercise both directions and assert old-to-new defaults, new-to-old removed-field errors,
  added/removed cases, and flags defaults.
- A required non-defaultable addition is refused with a `ContractError`.
- A changed alias target or changed type is refused.
- `--check` treats `convert.rs` as shared generated output and reports missing, changed, and
  extra files.
- A root with one version emits no `convert.rs`.

## 10. JSON Schema emitter

`witforge schema <wit-root> --out <dir> [--check] [--released <path>]` writes one Draft 7 JSON
Schema document per version and one per dependency:

```text
<out>/v<major>_<minor>.schema.json
<out>/<namespace>.<package>.v<major>.schema.json
```

Every version is validated and lockfile-checked like the other generators. The output is
value-oriented and has no root instance type: a consumer selects a definition with a JSON
Pointer `$ref` under `#/definitions/`.

### 10.1 Header and document shape

The first line is a valid JSON object prefix that also serves as the generated-file ownership
header:

```json
{"$comment":"@generated by witforge; do not edit.",
```

A foreign definition is referenced by a relative file and JSON Pointer, such as
`example.shared.v0.schema.json#/definitions/types~1item`; keep the generated schema files
together so the reference resolves.

The rest of the document is conventional JSON:

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "example:plugin@0.1.0",
  "definitions": {
    "types/span": { ... }
  }
}
```

- `$schema` is Draft 7.
- `title` is the package identity and exact version.
- `definitions` contains every named type in every interface, in interface and type source
  order. Keys are canonical WIT identities `interface/type`.
- A `$ref` uses JSON Pointer escaping: `/` becomes `~1` and `~` becomes `~0`, so
  `types/span` is `#/definitions/types~1span`.
- WIT docs on a type become a JSON Schema `description`; empty docs are omitted.
- The first line, LF line endings, final newline, deterministic ordering, output-root rules,
  stale-file removal, and `--check` behavior are the same ownership rules as section 1.

### 10.2 Type mapping

| WIT | Draft 7 schema |
|---|---|
| `bool` | `{"type":"boolean"}` |
| `u8`, `u16`, `u32`, `u64` | `{"type":"integer","minimum":0,"maximum":...}` |
| `s8`, `s16`, `s32`, `s64` | `{"type":"integer","minimum":...,"maximum":...}` |
| `f32`, `f64` | `{"type":"number"}` |
| `string` | `{"type":"string"}` |
| `list<T>` | `{"type":"array","items":<T>}` |
| `option<T>` | `{"anyOf":[<T>,{"type":"null"}]}` |
| record | object with every field in `properties`, every field in `required`, and `additionalProperties:false` |
| variant | `oneOf` of case objects; a case is one property named after the case, required, with its payload schema or `{"type":"null"}` |
| enum | `{"type":"string","enum":[...]}`; closed |
| flags | object with one required boolean property per flag and `additionalProperties:false` |
| `result<ok, err>` | `oneOf` of `{"ok":...}` and `{"err":...}` objects, or the one present side; `result` with no sides is an empty object |
| named `list`/`option`/`result` | the corresponding wrapper schema, stored under its definition |
| alias and `use` alias | the target schema; a named target is a `$ref` |

Record fields are always required, even when their type is `option<T>`; an optional field is
present with `null` rather than absent. A record, result object, and flags object reject unknown
properties. A variant/result case object rejects the other case and unknown properties, so
`oneOf` enforces exactly one case. A result side with no payload has no property.

### 10.3 Dependencies and testing

The emitter writes JSON directly and adds no runtime dependency. Tests use `serde_json` and the
dev-only `jsonschema` validator to compile the Draft 7 document and validate representative
instances, including required fields, primitive bounds, nested lists/options, result cases,
variant cases, closed enums, aliases, and named structural types. Golden output covers every
mapping row.

## 11. Configuration file

The generator commands accept an explicit TOML configuration file:

```text
witforge rust   --config witforge.toml [--project NAME]
witforge proto  --config witforge.toml [--project NAME]
witforge schema --config witforge.toml [--project NAME]
witforge glue   --config witforge.toml [--project NAME]
```

`check` and `lock` do not read configuration files: they operate on one version directory, and
the existing command line remains the fallback for every command.

### 11.1 Format

```toml
version = 1

[project.alint]
root = "wit"
released = "wit/released"

[project.alint.rust]
out = "src/plain"
serde = true

[project.alint.proto]
out = "proto"

[project.alint.schema]
out = "schema"

[project.alint.glue]
out = "src/glue"
plain-root = "crate::plain"
proto-root = "crate::proto"
```

- `version` is required and must be `1`.
- `project.<name>` is a project table; at least one is required. Project names are TOML keys.
- `root` is required for each project.
- `released` is optional; when absent the generator's normal default applies.
- `rust`, `proto`, `schema`, and `glue` sections are optional. Each output section has an `out`
  path; `rust` also has optional `serde = true|false`; `glue` also has optional `plain-root` and
  `proto-root` strings.
- Unknown keys or sections are errors, as are a missing/unsupported version, an empty project
  table, a missing project selected with `--project`, and a missing output section or CLI path
  needed by the selected command.
- Paths in the configuration file are resolved relative to the file that contains them; absolute
  paths are used as written. They are not expanded through `~`.
- The configuration is not discovered implicitly. It is read only when `--config <file>` is
  passed.

### 11.2 Precedence and selection

- `--project <name>` selects a project. If the file has exactly one project, it is selected by
  default; if it has more than one, `--project` is required.
- `--project` without `--config` is an error.
- For every path, an explicit CLI value wins over the selected project: positional `WIT_ROOT`
  overrides `root`; `--out` overrides the matching output section's `out`; `--released`
  overrides project `released`; `--plain-root` and `--proto-root` override the `glue` section.
- Config-only invocation (`witforge rust --config ...`) and CLI-only invocation
  (`witforge rust <root> --out ...`) are both valid. The configuration is validated even when
  CLI flags override all of its values.
- `--serde` and `--no-serde` override the `rust` section's `serde` value. `--check` has no
  configuration key: it is an action, not a project setting.

### 11.3 Testing requirements

- A single-project configuration resolves root and all four emitters.
- CLI flags override configuration paths.
- Multiple projects require `--project`, and selecting a project uses its root and outputs.
- Unknown keys, missing projects, missing `--config` for `--project`, and missing output values
  are errors.
- The existing CLI-only form continues to work.
