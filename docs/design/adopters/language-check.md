## Current architecture

Language Check has four related but deliberately different contract surfaces.

### Engine boundary

The Rust [`Engine`](https://github.com/KaiErikNiermann/LangCheck/blob/cc32d5ae31b43baba1350159bbd8a7a9b3efec96/rust-core/src/engines/mod.rs#L25-L69) trait receives one extracted prose range plus a BCP-47 natural-language tag and returns internal diagnostics. Its async and batch methods, engine selection, caching, language support, and failure reporting are application/runtime policy; they are not candidates for witforge generation.

The internal `checker::Diagnostic` and `checker::Severity` are generated by prost from [`proto/checker.proto`](https://github.com/KaiErikNiermann/LangCheck/blob/cc32d5ae31b43baba1350159bbd8a7a9b3efec96/proto/checker.proto). That protobuf is the editor/core process protocol. It includes request envelopes, a service, settings maps, extraction metadata, engine health, cache state, configuration probes, initialization, and editor-specific diagnostic fields.

### External-process checker

[`ExternalEngine`](https://github.com/KaiErikNiermann/LangCheck/blob/cc32d5ae31b43baba1350159bbd8a7a9b3efec96/rust-core/src/engines/mod.rs#L730-L866) launches one process per check with bounded stdin/stdout and timeout handling. It serializes a private Rust `ExternalRequest { text, language_id }` to JSON and deserializes a private `ExternalDiagnostic` list.

The diagnostic decoder requires `start_byte`, `end_byte`, and `message`. It supplies these defaults when fields are absent:

- `suggestions`: empty list;
- `rule_id`: empty string, later namespaced with the provider name;
- `severity`: protobuf numeric warning value `2`;
- `confidence`: serde produces `0.0`, then the adapter changes non-positive values to `0.7`.

A missing command, timeout, non-zero exit, oversized output, or malformed JSON is now an error. Commit [`97e0071`](https://github.com/KaiErikNiermann/LangCheck/commit/97e0071) changed command-line checker failures from clean empty answers to reported failures because empty results were cached as successful checks.

### Extism checker

[`WasmEngine`](https://github.com/KaiErikNiermann/LangCheck/blob/cc32d5ae31b43baba1350159bbd8a7a9b3efec96/rust-core/src/engines/mod.rs#L868-L993) retains Extism's `check` byte/string ABI. It builds the same two-field JSON request and uses the same private `ExternalDiagnostic` decoder. It deliberately differs from the process path on runtime errors: Extism call and output-parse failures warn and return an empty diagnostic list.

The maintained [Go/TinyGo reference plugin](https://github.com/KaiErikNiermann/LangCheck/tree/cc32d5ae31b43baba1350159bbd8a7a9b3efec96/plugins/wordiness-check) hand-defines the request, diagnostic, and severity constants. Its [Rust integration tests](https://github.com/KaiErikNiermann/LangCheck/blob/cc32d5ae31b43baba1350159bbd8a7a9b3efec96/rust-core/tests/wasm_plugin.rs) run the committed component through Extism and check diagnostics, offsets, suggestions, and namespacing. The dedicated [plugin workflow](https://github.com/KaiErikNiermann/LangCheck/blob/cc32d5ae31b43baba1350159bbd8a7a9b3efec96/.github/workflows/wasm-plugin.yml) runs Go tests, rebuilds the Wasm artifact, and runs the Rust integration test.

### Editor protobuf and public extension API

The editor/core protobuf is related but not the same contract:

- protobuf `CheckRequest` adds `settings: map<string, string>` and optional `file_path`;
- protobuf `Diagnostic` adds normalized ID, natural-language context, and pack-installability fields;
- protobuf `CheckResponse` adds extraction details, engine health, and cache provenance;
- the service and request/response envelopes own process framing and editor operations.

The TypeScript [`LanguageCheckDiagnostic` and `ExternalProviderRegistration`](https://github.com/KaiErikNiermann/LangCheck/blob/cc32d5ae31b43baba1350159bbd8a7a9b3efec96/extension/src/api.ts) are another manually declared API. The registered provider callbacks are stored in a private map, but current source has no reader or invocation of that map; this is not counted as a maintained execution path for the proposed slice. Commit [`3968bc9`](https://github.com/KaiErikNiermann/LangCheck/commit/3968bc9) fixed a real numeric-severity mapping defect in this public API.

The editor protobuf must remain separate. Witforge does not emit protobuf services, process envelopes, maps, or editor lifecycle policy, and replacing this working protocol is not part of the adoption hypothesis.

## Problem evidence

### Observed: one public JSON contract is repeated

The external-process and Extism execution paths share the same semantics, but those semantics are represented in multiple separately edited forms:

1. private Rust `ExternalRequest`;
2. a second request built with `serde_json::json!` in `WasmEngine`;
3. private Rust `ExternalDiagnostic` plus adapter defaults;
4. Go `CheckRequest`, `Diagnostic`, and severity constants in the reference plugin;
5. the [external-provider guide](https://github.com/KaiErikNiermann/LangCheck/blob/cc32d5ae31b43baba1350159bbd8a7a9b3efec96/docs/advanced/providers.md);
6. the [Wasm plugin guide](https://github.com/KaiErikNiermann/LangCheck/blob/cc32d5ae31b43baba1350159bbd8a7a9b3efec96/docs/guide-wasm-plugin.md) and shorter plugin reference.

The Rust diagnostic decoder is already shared between the process and Extism hosts. The duplication problem is therefore not “two Rust implementations”; it is the lack of one versioned public contract across host types, reference-plugin types, examples, and documentation.

### Observed: the copies have drifted

Three current inconsistencies are directly visible at `cc32d5a`:

- The external-provider guide says severity `1=Error` and `3=Info`; protobuf, Rust code, the Wasm guide, and the Go reference define `1=Information` and `3=Error`.
- The Wasm guide's request example calls `language_id` `"markdown"`; the external-provider guide says it is a BCP-47 natural-language tag such as `en-US`, and the orchestrator passes the resolved natural language to every engine.
- The external-provider guide says process failures and malformed JSON are logged as no diagnostics; current process-engine code returns an error after `97e0071`. The Extism path still warns and returns no diagnostics, so the difference is runtime policy rather than a shared value-contract field.

These are objective maintenance defects. Witforge would not automatically update prose guides or Go code, but a checked WIT package, generated host types, locked changes, and shared JSON fixtures would establish a reviewable source and make drift harder to introduce.

### Observed: the contract has no explicit version

The Extism export name is `check`; the process path has no handshake; neither JSON request carries a contract version. The project is actively released and early-development, but no plugin compatibility policy or frozen historical plugin fixture was found. This is evolution pressure, not evidence of an existing compatibility promise.

### Hypothesis: maintainers want a generated contract dependency

No maintainer has stated that the duplication is painful or that adding witforge-generated files is desirable. The repository already keeps the JSON shape small, and its reference plugin is Go rather than Rust. The benefit could be too small relative to another generator and committed-output check. This is the central question for outreach, not a fact established by code similarity.

## Capability classification

### Solved now by witforge

A WIT-owned plugin slice can use witforge 0.4.3 today for:

- subset checking and a committed contract version;
- stable member/method identity and explicit compatibility diff;
- generated owned Rust request/diagnostic types and object-safe checker trait;
- Serde decoding/encoding for the current snake_case JSON field names;
- deterministic generated-output checks;
- optional protobuf messages and glue if a future consumer actually needs them;
- adjacent-version adapters after a second contract version exists.

### Upstream contract decisions

Language Check must decide:

- whether `language_id` is normatively a BCP-47 natural language for both plugin paths;
- whether omitted diagnostic fields and their current defaults are contractual;
- whether `null` should be accepted for optional fields;
- whether the plugin contract should gain an explicit WIT package version while Extism/process framing remains unchanged;
- whether generated Rust and a wire lock remove enough maintenance to justify adoption.

Those are product/API decisions, not witforge defects.

### Bounded witforge limitations

The current JSON Schema emitter cannot describe the public JSON wire exactly:

- WIT `language-id`, `start-byte`, and `rule-id` become kebab-case JSON Schema properties, while generated Rust Serde and the current plugin wire use snake_case;
- record properties remain required even when their WIT value is `option<T>`, whereas the current plugin decoder permits those fields to be absent;
- generated Serde serializes `None` as JSON `null`, while the current `Vec`, `String`, `i32`, and `f32` decoder fields reject `null`.

The Rust host can still preserve current inputs by using generated `Option` fields and applying existing defaults in an adapter. The generated JSON Schema must not be advertised as the plugin-wire schema. If maintainers require one generated schema that exactly describes current JSON omission and naming, a separately scoped witforge feature with behavioral tests is required.

Witforge also does not generate Go types. The Go reference plugin remains hand-written and should consume shared JSON conformance fixtures if adoption proceeds. Direct Go generation is outside witforge's current mission.

### Runtime and application concerns

These remain entirely with Language Check and Extism/process tooling:

- Extism manifest, sandbox, call, and failure behavior;
- process spawning, framing, timeouts, output limits, and crash policy;
- engine language/extension selection and batching;
- rule-ID namespacing and default application;
- editor protobuf service, envelopes, settings, health, extraction, and cache state;
- plugin discovery, installation, and distribution.

### No demonstrated problem

Stable protobuf identity is not a current need for the plugin JSON contract. The existing protobuf editor protocol is generated correctly from its own `.proto` source and should not be migrated merely to make witforge emit protobuf. Generated glue is technically valid but has no present consumer in this slice.

## Smallest useful adoption slice

### Proposed WIT shape

The disposable model used this semantic shape:

```wit
package language-check:plugin@0.1.0;

interface checker {
  type severity = s32;

  record plugin-input {
    text: string,
    language-id: string,
  }

  record diagnostic {
    start-byte: u32,
    end-byte: u32,
    message: string,
    suggestions: option<list<string>>,
    rule-id: option<string>,
    severity: option<severity>,
    confidence: option<f32>,
  }

  check: func(input: plugin-input) -> list<diagnostic>;
}

world plugin { export checker; }
```

`severity` is an `s32` alias, not a WIT enum: the current JSON wire is numeric, current decoding accepts any `i32`, and a derived Rust Serde enum would serialize names instead of the existing numbers.

The record is named `plugin-input`, not `check-request`. The initial model used `check-request`; witforge correctly rejected it because the type and the generated request message for function `check` both produced protobuf name `CheckerCheckRequest`.

### Upstream integration boundary

If maintainers confirm interest:

1. add a versioned WIT package and wire lock;
2. commit generated Rust with Serde and a stale-output CI check;
3. replace `ExternalRequest` and the Wasm request macro with generated `PluginInput`;
4. decode generated optional `Diagnostic`, then apply existing empty/warning/0.7 defaults in one application adapter;
5. retain the Extism and subprocess calls exactly as they are;
6. retain `proto/checker.proto` and the TypeScript editor protocol exactly as they are;
7. retain the Go reference structs, but run shared full/minimal JSON fixtures against both Go and Rust;
8. update both plugin guides from the agreed semantic contract;
9. do not publish the current witforge JSON Schema as the plugin JSON schema.

Rollback is removal of the generated module and restoration of the two private Rust input/diagnostic definitions; no persisted data or current protobuf wire changes.

### Success checks

An upstream experiment must prove:

- full current request/diagnostic JSON remains byte-field compatible;
- absent optional fields receive the current defaults;
- the decision for `null` is explicit and tested;
- severity `1/2/3/4` semantics agree across Rust, Go, docs, editor API, and protobuf;
- `language_id` has one documented meaning;
- existing Go Wasm integration tests still pass;
- external-process success, malformed output, non-zero exit, timeout, and oversized output behavior is unchanged;
- Extism failure behavior remains unchanged;
- generated output is deterministic and checked in CI.

## Disposable compatibility exercise

The exercise used witforge 0.4.3 from this repository and Language Check `cc32d5a` as the semantic reference.

Observed results:

- `lock --first` and `check` passed after the `plugin-input` naming correction;
- Rust with Serde, protobuf, JSON Schema, and glue generation passed;
- all four emitters accepted their generated output with `--check`;
- generated Rust used `String`, `u32`, `i32`, `f32`, `Vec<String>`, and `Option` only;
- the full current request and diagnostic JSON decoded, and numeric severity remained numeric;
- omitted diagnostic fields decoded as `None`, enabling the current default adapter;
- unknown request fields were ignored, matching serde's current forward-compatible default;
- serializing absent generated options produced explicit JSON `null` fields;
- generated JSON Schema rejected the current snake_case request and diagnostic, used kebab-case properties, and required option-valued properties;
- a schema-conformant kebab-case/full-property diagnostic passed that schema;
- generated protobuf and glue succeeded but no current Language Check plugin path consumes them.

Language Check's current `cargo test --locked` passed **907 tests across 24 suites, with 3 ignored** at `cc32d5a`. The reference Go plugin's `go test ./...` passed. The two relevant extension suites passed **28 tests**, generated the protobuf TypeScript surface, and `pnpm typecheck` passed. These runs validate the reviewed upstream behavior; they do not make the disposable WIT an adopted contract.

## Recommendation

**Contact.** The maintained contract is unusually well bounded, two real execution paths share it, and current documentation drift demonstrates an objective source-of-truth problem. Witforge can solve part of that problem without replacing Extism, subprocess execution, or editor protobuf.

The recommendation is deliberately narrower than “adopt witforge”:

- ask whether maintainers consider the duplication and drift a problem;
- disclose the JSON Schema naming/omission limitation and lack of Go generation;
- offer only a contract/type-generation experiment after explicit interest;
- do not submit implementation code under `W11-006` or before `W11-017` records maintainer direction.

No witforge implementation task is created now. If maintainers require exact generated JSON Schema or custom Serde defaults/names, their confirmed requirement must become a separately scoped tested task.

## Falsifier

Change this recommendation to **no-contact/no-go** if maintainers say the plugin JSON is intentionally informal or disposable, do not want generated Rust/lock artifacts, or value the existing hand-written multi-language simplicity more than versioned contract checking.

Change it to **defer** if maintainers want one generated JSON Schema that exactly preserves current snake_case and omitted-field behavior before considering adoption; witforge 0.4.3 does not provide that artifact.
